# 스킬 중복 정리 절차

카탈로그에 같은 문서가 여러 id로 들어와 있다. 이 문서는 **무엇을 근거로, 어떤 순서로, 누구에게 물어서**
정리할지를 정한다. 후보 목록은 AX 대시보드 → 스킬 → **카탈로그 중복** 탭이 자동으로 만든다.

관련: [DEV-4281](https://linear.app/geniefy/issue/DEV-4281) · 병목 진단은 [DEV-4275](https://linear.app/geniefy/issue/DEV-4275)

## 왜 정리가 먼저인가

2026-09-04 실측에서 발행된 스킬 491개 중 **312개(64%)가 한 번도 로드되지 않았다.**
적용된 100개 중 73개(73%)는 한 사람만 썼다. 검색에는 뜨는데 열지를 않는다 —
**몰라서 못 쓰는 게 아니라 고를 수가 없다.** 그래서 알림([DEV-4280](https://linear.app/geniefy/issue/DEV-4280))보다 정리가 앞선다.

## 후보는 어떻게 나오나

`packages/lib/src/features/ax/skill-duplicates.ts`가 본문의 문자 3-그램 자카드 유사도를 잰다.

| 값 | 의미 |
| -- | -- |
| **0.50 이상** | 후보 쌍으로 화면에 올린다. "사람이 봐야 한다"는 뜻이지 "합쳐라"가 아니다 |
| **0.90 이상** | 판단 단위 묶음으로 이어 붙인다 |
| **0.99 이상** | 공백·머리말을 정리하면 사실상 같은 문서 |

### 두 가지 함정 (실측으로 확인함)

**하나 — 본문을 자르면 오탐이 생긴다.** `skill-diff` 패널은 비용 때문에 앞 8,000자만 비교한다.
그 기준으로 재면 170쌍이 나오는데 자르지 않고 재면 134쌍이다. 사라진 36쌍은 전부 gstack 계열로,
도입부가 비슷하고 본론이 다른 문서였다 (`gstack-setup-browser-cookies` ↔ `gstack-ship` 0.938 → **0.428**).
그래서 이 패널은 자르지 않는다.

**둘 — 낮은 유사도로 묶으면 사슬이 생긴다.** 0.5로 이어 붙이면 gstack 계열 17개가 줄줄이 엮여
묶음 하나가 된다. 그건 판단 단위가 아니다. 그래서 묶음은 0.90 이상만 잇고, 그 아래는 쌍으로만 보여준다.

**포크 관계는 못 쓴다.** `catalog_items.forked_from`이 491개 전부 NULL이다. 유사도가 유일한 단서다.

## 무엇을 고르나

묶음 하나에 결정 하나를 내린다. 아래 순서로 판단한다.

### 1. 폐기 — 같은 문서가 여러 id로 있고, 그중 하나만 쓰인다

가장 흔한 형태다. 커뮤니티 스킬을 이름만 바꿔 두세 번 등록한 경우가 여기 해당한다.

- **남길 것**: 적용 이력이 있는 id (화면에서 `사용` 표시가 붙는다). 이력이 전부 없으면 이름이 가장
  설명적인 것을 남긴다
- **지울 것**: 나머지
- 지우기 전에 **검색 유입을 확인한다.** 지울 id가 검색 결과로 나온 적이 있다면 그 검색어가
  남길 id로도 닿는지 본다. 안 닿으면 남길 쪽 설명·태그를 먼저 보강한다

### 2. 분리 유지 — 의도적으로 갈라놓은 것

같은 저장소에서 가져온 워크플로 단계처럼, 어휘가 겹칠 뿐 하는 일이 다른 경우다.
gstack 계열이 대표적이다. **유사도가 높다는 이유만으로 합치지 않는다.**

판단 기준: 두 문서의 **결론부**(무엇을 하라는 지시)가 다르면 분리 유지다. 도입부·설명이 같은 것은 근거가 아니다.

분리 유지로 결정하면 이 문서 맨 아래 "분리 유지 결정" 표에 적는다. 다음 사람이 같은 판단을 다시 하지 않게.

### 3. 병합 — 둘 다 쓰이는데 내용이 갈라진 경우

양쪽 다 적용 이력이 있고 내용이 드리프트된 상태. 가장 드물고 가장 비싸다.
한쪽으로 합치고 나머지를 지우되, **양쪽 사용자에게 먼저 알린다.**

## 누구에게 묻나

**작성자 필드는 믿을 수 있다** — 2026-09-04에 확인했다. 다만 491개 중 348개(71%)가 한 계정에 몰려 있고,
그건 저작이 아니라 **대량 등록**이다 (하루 89개, 1분에 38개가 들어온 구간이 있다).

그래서 소유자 확인을 이렇게 나눈다:

| 대상 | 확인 방법 |
| -- | -- |
| 작성자 없음 (`community-*` 등) | 확인 없이 처리 가능. 사내 저작물이 아니다 |
| 대량 등록분 중 **적용 이력 0건** | 등록자에게 묶음 단위로 한 번에 알린다. 개별 확인 안 받는다 |
| **적용 이력이 있는 것** | 적용한 사람에게 개별로 묻는다. 등록자만으로 부족하다 |

**348개를 한 사람에게 한꺼번에 묻지 않는다.** 답을 못 받는다. 묶음 5~10개씩 끊어서 보낸다.

## 어떻게 지우나

- 카탈로그 삭제는 **운영 쓰기다. 사용자 승인 없이 실행하지 않는다.**
- 지우기 전에 참조를 확인한다: `skill_events` · `item_versions` · `catalog_item_tags` ·
  `catalog_item_translations` · `package_items`. 태그·번역·버전·패키지는 CASCADE로 함께 지워진다
- **정규식으로 지우지 않는다.** id 목록을 먼저 뽑아 눈으로 확인하고, 그 목록만 대상으로 삭제한다
  (2026-09-04 테스트 픽스처 정리에서 처음 쓴 패턴이 30건 중 20건만 잡았다)
- 지운 행은 백업해 둔다 (`embedding` 제외)
