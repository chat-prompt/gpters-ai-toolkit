# Slack 보고 → AX 최종 검토

## 구현 상태

2026-09-10 로컬 구현 및 검증 완료. 운영 배포·DB 마이그레이션·접수 활성화와 실제 에이전트의 합성 보고 파일럿은 아직 진행하지 않았다. 기존 npm 패키지 발행이나 수집기 변경은 필요하지 않다.

사람이 슬랙에서 특정 에이전트에게 보고를 요청하거나, 에이전트가 제안한 보고를 사람이 명시적으로 승인하면 에이전트의 기존 인증으로 접수한다. 대시보드에서 지정된 최종 검토자가 추가 확인·확정·오탐·수정·재검증을 판정한다. [실행 및 API 프로토콜](../../infra/agent-reports/PROTOCOL.md)에 익명 예제와 저장·접근 경계를 적었다.

## 운영 에이전트와 확인한 조건

- 채널·메시지·스레드 시각과 발신자 ID로 문제 및 승인 메시지 링크를 만들 수 있다.
- 구조화된 승인 플래그는 없다. 이 에이전트에게 직접 한 텍스트 요청만 승인으로 해석한다. 제3자에게 한 말·리액션·인용·봇 메시지는 제외한다.
- 기존 에이전트 인증을 재사용할 수 있다. 배포 권한이나 개인 기기 로그인은 추가하지 않는다.
- 작업 ID가 없는 답변 품질 문제도 접수해야 한다. 실행 기록을 꾸며 만들지 않으며 모르는 모델·작업 ID는 생략한다.
- 현재 대화 스레드에서 접수 영수증과 후속 문답을 이어간다. 세션 종료 후에도 자동 감시한다고 약속하지 않는다.

서버는 승인 링크 형식·워크스페이스를 검증하지만 Slack 원문의 승인 여부를 독립 검증하지 않는다. 승인과 재검증은 에이전트가 전달한 주장으로 표시하고 최종 검토자가 연결된 원문을 확인한다.

## 구현 및 경계

- `POST /api/ax/agent-reports`: 조직·에이전트·문제 메시지 링크로 중복 방지. 동일 재전송은 기존 영수증, 내용 변경은 409와 보완 안내.
- `GET/POST /api/ax/agent-reports/{id}`: 본인 보고 조회·보완만 허용. 보완은 고정 updateId로 중복을 막고 사람의 판정을 변경하지 않는다.
- 기존 `ax_incident_reviews` JSON 원장을 재사용한다. 생성 충돌 및 revision 조건부 갱신으로 동시 보완·판정을 보존한다.
- 사람의 판정은 내부 관리자이면서 `AX_INCIDENT_REVIEWER_IDS`에 있는 사용자만 가능하다. 미설정은 저장 불가다.
- 보고 상세에는 기대·실제 결과, 문제·승인 링크, 검토 이력과 보완 자료를 표시한다. 영수증 URL은 해당 상세를 바로 연다.
- 수집기가 응답하지 않아도 저장된 보고는 검토할 수 있다. 보고에서 가짜 실패 이벤트나 성공률을 만들지 않는다.
- 수정 후 재검증 근거가 없거나 최신 결과가 실패/판정 불가이면 완료를 승인할 수 없다. 사람이 근거를 확인한 완료와 자동 관측 표본을 구분한다.
- repo에서 빌드한 helper는 기존 에이전트 인증만 읽는다. 서버 origin 일치, 리다이렉트 금지, 30초 제한, 소유한 0600 입력 파일 및 16KB 제한을 적용한다.

## 검증

- 웹 단위 테스트 전체 129개 파일, 2,721개 통과. 기본 실행에서 격리 DB 테스트 2개 제외. 이후 요청 크기 제한 테스트를 추가해 관련 HTTP/UI 12개와 보고 상태 전이 테스트를 재검증했다.
- 별도 로컬 PostgreSQL DB에서 초기 0건 확인 후 0040만 적용했다. 동시 저장, 오래된 revision 거부, 연결 재개, 중복 접수, 타 에이전트·조직 접근 거부 및 원천 수집 없는 보고 검토를 검증했다(2개 통과).
- 앱 소스와 helper 타입 검사, 변경된 웹 코드 ESLint, helper Bun 빌드 및 인증 경계 단위 테스트 통과.
- 데스크톱 밝은/어두운 테마, 390px 화면에서 실제 브라우저 검수. 상세 바로가기, 두 근거 링크, 추가 확인 요청 저장과 이력을 확인했다. 가로 넘침 없음.
- 운영·공유 DB를 대상으로 API/E2E 전체 테스트를 실행하지 않았다. 미리보기는 브라우저에만 저장하는 합성 데이터다.

## 다음 활성화 순서

1. 변경 코드 검토 후 대시보드 배포. 운영 DB 브랜치·복구 지점을 확인하고 0040 적용 및 스키마를 대조한다.
2. 검토 저장소와 내부 조직·Slack 호스트·최종 검토자 ID를 비공개 환경변수로 설정한다. 지정 검토자와 다른 계정의 권한을 대조한다.
3. 접수 스위치를 열고 승인된 에이전트 하나에서 명확히 합성으로 표시한 보고를 접수한다. API 영수증 → 대시보드 → 같은 슬랙 스레드 회신 → 추가 확인·보완을 대조한다.
4. 파일럿 검토 후 다른 에이전트에 동일 프로토콜을 적용한다. 실행 환경별 수집기 상태와 보고 접수 상태는 별개로 유지한다.

실제 자동 inbox 감시·Slack 푸시, 원천 로그 자동 첨부, 과거 원장 이관과 장기 페이지네이션은 이번 범위에 없다. 접수 또는 검토 스위치를 끄면 해당 API가 닫히며 원장 데이터는 보존된다.
