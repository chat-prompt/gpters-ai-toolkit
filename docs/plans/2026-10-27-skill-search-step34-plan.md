# 스킬 검색 3·4단계 개선과 두 길 비교 계획 (DEV-4727 · DEV-4729)

작성 2026-10-27, 고침 2026-10-28. 이 문서는 무엇을 어디서 바꾸고 두 길을 어떻게 비교할지 정한다. 결론: 처음 판 3·4단계를 그대로 두고 1단계 문장만 바꾼다. 작업 폴더에 반영한 것은 9절 끝, 실제 세션 테스트와 4단계 채점표는 10절에 있다. 아직 커밋하지 않았다.

## 0. 전제

- 검색은 4단계다.
  1. AI가 검색어와 작업 설명을 써서 검색한다.
  2. 서버가 임베딩 점수로 정렬한다. JEV 키가 있으면 JEV가 다시 정렬한다.
  3. AI가 결과 목록에서 불러올 스킬을 고른다.
  4. AI가 SKILL.md 본문을 읽고 쓸지 정한다.
- 이미 정한 것: 임베딩은 이름·설명·태그, 임계값 0.40, 결과 최대 5개 (DEV-4729 댓글 10/27).
- 비교할 두 길
  - 길 1: 임베딩 → JEV → 상위 5개를 모두 불러옴(3단계 없음) → 4단계
  - 길 2: JEV 없이 임베딩 → AI가 목록에서 고름(3단계) → 4단계
- 하지 않는 것: 운영 DB 쓰기, 운영 배포, 운영 서버 호출, git 커밋·푸시, 의존성 설치, 키 요청. 실험은 로컬 aitk2 서버(127.0.0.1:3100, DB `aitk2`)에서만 한다.

## 2. 공통 수정 (두 길에 똑같이)

두 길의 차이는 3단계 문장뿐이어야 한다. 그래서 1단계와 4단계 안내는 두 길에 같은 문장을 쓴다. 3단계 규칙은 공통 문장에 남기지 않는다. 매 질문 힌트(`skill-search.sh:17`, `:24`)에도 "0.40 이상→로드, 미만→스킵"이라는 3단계 규칙이 들어 있다. 그래서 힌트에서는 이 줄을 빼고 "자세한 절차는 skill-suggest SKILL.md"만 남긴다.

### C1 문장 (1단계 검색어·맥락)

1회차 결과에서 정답을 놓친 가장 큰 원인이 1단계였다(정답 있는 41개 중 두 길 모두 10개가 검색 결과 5개 안에 정답이 없음). 사용자 원문을 서버로 보내는 방법은 개인정보와 길이 문제로 하지 않는다(10/27 재민님 결정).

1. 검색어에는 사용자가 하려는 일(동사)과 그 재료·대상(도구·파일·서비스 이름)을 넣습니다. 대화에 스킬 ID나 이름이 나왔으면 검색어 맨 앞에 그대로 넣습니다. 단어 수는 제한하지 않습니다. (10/27 정함)
2. 맥락에는 지금까지 진행한 일, 결과물을 어디에 쓸지, 이미 정해진 조건(언어, 도구, 형식)을 씁니다. 검색어와 같은 말을 되풀이하지 않습니다. 맥락은 비워 두지 않습니다. 대화가 처음이라 배경이 없으면 사용자가 원하는 결과물을 한 줄로 씁니다. (10/28 고정. 10/27 문장에서 "검색어에 넣지 않은 배경을 씁니다"만 뺐다. 짧은 예시 3개를 같이 둔다. 짧은 맥락 문장 네 가지는 34~36으로 차이가 없었고 이 문장이 36이었다. 긴 맥락(500~660자)은 31~32로 나빴다. 스킬 쪽 임베딩 글(이름·설명·태그)이 중간값 180자라 맥락이 길면 검색어 비중이 줄어든다. 근거는 `experiments/2026-10-27-step34/2026-10-28-grading.md` "맥락 길이 비교")

### C2·C3 문장

1. 본문을 읽고 "언제 쓰나(트리거)", "필요한 입력", "만들어 내는 결과물" 세 가지를 지금 사용자 요청과 맞춰 봅니다. 본문에 이 내용이 없으면 설명(description)과 첫 문단으로 판단합니다. (10/27 정함)
2. 결과물이 맞으면 적용합니다. 트리거나 입력이 조금 다르면 맞춰 쓸 수 있는지 보고 정합니다. 결과물이 다르면 적용하지 않습니다. (10/27 정함)
3. 맞는 스킬이 여럿이면 결과물이 가장 가까운 1개만 적용합니다. (10/27 정함)
4. 이미 설치된 스킬이나 내장 기능(예: code-review)이 팀 스킬보다 결과물에 더 가까우면 그것을 씁니다. 불러온 팀 스킬은 적용하지 않은 것으로 보고하고, 이유에 무엇을 대신 썼는지 적습니다. (10/28 정함. 1회차 실험에는 이 문장이 없었다)
5. 불러왔지만 적용하지 않기로 했으면 이유를 한 줄로 보고합니다. MCP는 `report_skill_outcome(applied=false)`, CLI는 `aitk report-outcome --applied false`입니다. (C3 문장, 10/27)

## 3. 길별 수정

플러그인 파일은 실험 중에 저장소에서 바꾸지 않는다. 임시 폴더에 길별로 복사하고 `claude --plugin-dir`로 각각 쓴다. 저장소에는 이긴 길만 반영한다.

### 길 2 (JEV 없음, AI가 고름)

- 3단계 문장(`SKILL.md:76~103` 대체)
  - 목록의 이름·설명을 읽고 지금 작업에 바로 쓸 스킬을 고른다. 점수는 참고값이다.
  - 0.40을 기본으로 하되, 0.40 미만이어도 이름·설명이 딱 맞으면 불러와도 된다.
  - 기본 1개를 불러온다. 작업의 서로 다른 부분을 맡으면 2개까지 불러온다. 2개가 맞는지는 실험 뒤에 다시 본다.
  - 맞는 게 없으면 스킵 사유를 보고한다(지금 B와 같다).
  - 위 세 가지는 10/27 재민님이 정했다.
- JEV를 끄는 방법
  - 로컬 `.env.local`에는 `TYPESAFE_API_KEY`가 없어서 JEV가 켜지지 않는다(`rerank.ts:58`).
  - 실험 뒤에 로컬 DB `mcp_audit_logs`의 검색 결과에 `rerankScore`·`embeddingRank`가 하나도 없는지 확인한다.
  - 운영에서 길 2를 쓰려면 키를 빼거나, 이미 있는 `rerank` 옵션(`vector-search.ts:36`, 기본 true `:81`)을 MCP 인자로 열어야 한다. 지금은 `tools.ts`에 이 인자가 없다. 운영 반영 때 정한다.

### 길 1 (JEV, 상위 5개를 모두 불러옴)

- 1위만 불러오지 않는다. 운영 기록에서 JEV가 1위를 바꾼 34건 중 JEV 1위가 정답인 건 13건뿐이었다(DEV-4729 댓글 10/27). 그래서 상위 5개 본문을 모두 읽고 4단계에서 정한다(10/27 재민님 결정).
- 3단계 문장(`SKILL.md:76~103` 대체)
  - 결과가 있으면 목록에서 고르지 않고 결과 전부(최대 5개)의 본문을 불러온다. 점수는 보지 않는다.
  - 결과가 없을 때만 스킵 사유를 보고한다.
  - 점수를 보지 않으므로 JEV가 올린 0.40 미만 스킬도 읽는다. 대신 검색마다 본문을 최대 5개 읽어서 시간과 토큰이 늘어난다. 이 비용은 4절에서 잰다.
- 상위 5개를 다 읽으면 5개 안의 순서는 결과에 영향이 없다. JEV가 보탤 수 있는 건 후보 20개(결과 수의 4배) 중에서 임베딩 상위 5개 밖에 있던 정답을 5개 안으로 끌어올리는 것뿐이다.
- JEV 켜기: 로컬에 키가 없다. 그래서 길 1을 둘로 나눈다.
  - 길 1a (JEV 없이 상위 5개를 모두 불러옴): 지금 로컬 서버로 돌릴 수 있다. 길 2와 비교하면 "3단계가 있고 없고"의 차이만 남는다.
  - 길 1b (JEV + 상위 5개를 모두 불러옴): 재민님이 로컬 `.env.local`에 키를 직접 넣었을 때만 돌린다. 키는 요청하지 않는다. 1b는 같은 로컬 DB와 카탈로그를 쓰므로 길 2와 후보 집합이 같다.
  - 1b를 못 돌리면 결론은 "3단계가 필요한가"까지만 낸다. "길 1(JEV 포함) 채택"은 결론으로 쓰지 않는다. 운영 기록 채점은 JEV가 순서를 바꾼 결과만 봤다. 4단계까지 간 끝 결과는 재지 않았기 때문이다.
- JEV 문턱은 그대로 둔다(`rerank.ts:32`·`:34` 등). 임베딩 1·2위 차가 0.05 미만일 때만 JEV를 부른다. JEV가 확신할 때만 순서를 바꾼다. 운영 기록에서 순서가 바뀐 건 710건 중 147건이다. "항상 재정렬"로 바꿀지는 1b 결과를 보고 따로 정한다.

### 돌리는 방법
