# DEV-4485 — semantic_search 지연 변경 전 측정

작성 2026-09-21. 트랙 B(지연)의 1단계 산출물이다. 근거 문서는 `2026-09-21-aitk-search-rerank-and-latency-handoff.md` §3.

## 결론

**병목은 임베딩이 아니라 DB 호출이다. 그리고 DB 호출 시간의 약 99%는 쿼리 실행이 아니라 미국 동부(Vercel `iad1`)와 싱가포르(Neon) 사이의 네트워크 왕복이다.** DB 서버 안에서 쿼리가 실행되는 시간은 8.5ms다. 핸드오프가 가장 유력하다고 본 "쿼리 임베딩 캐시 외부화"는 이 측정으로 본선에서 내려간다.

- `semantic_search` 한 번의 `searchTime` p50은 **약 1,975ms**다. 이 중 DB SELECT 한 번이 p50 **1,375ms**(약 70%)를 차지하고, 임베딩은 p50 **553ms**다.
- 인메모리 임베딩 캐시는 12건 중 **0건 히트**했다. 같은 쿼리를 연달아 보내도 다른 인스턴스로 가서 빗나갔다. 로그의 `cacheSize`가 1~4로, 인스턴스가 짧게 살고 여러 개로 흩어진다.
- 따라서 캐시를 외부화해 임베딩을 전부 없애도 p50은 약 1.4초로만 내려간다. 목표 500ms에는 못 미친다.

## 방법

1. 운영 MCP(`https://ai-toolkit.gpters.org/api/mcp`)의 `semantic_search`를 읽기 호출로 불렀다. `_source: latency-measure`를 붙였고 `limit=5`를 썼다. 쿼리는 서로 다른 5개와 같은 쿼리 재호출 1회다.
2. 서버가 이미 남기는 로그 `Semantic search completed`(`packages/lib/src/search/vector-search.ts`)의 `embeddingMs`/`dbMs`/`totalMs`를 Vercel 런타임 로그에서 읽었다. 이번 측정 6건과 같은 날 앞선 운영 호출 6건을 합쳐 12건이다.

```bash
vercel logs --environment production --since 2h \
  --query "Semantic search completed" --json -n 100
```

`dbMs`는 `vector-search.ts`의 SELECT 한 번(`db.select(...).limit(limit)`)만 잰 값이다.

## DB가 느린 이유 — EXPLAIN 결과 (2026-09-21, 사용자 승인 후 읽기 전용 트랜잭션)

**DB 서버 안에서 실행된 시간은 8.5ms다.** `dbMs` 1,375ms의 나머지 약 99%는 네트워크다.

| 항목 | 값 |
|---|---|
| 앱 쿼리 `Execution Time` (Seq Scan 500행 → top-N heapsort) | 8.5ms |
| 순수 거리 정렬(`ORDER BY embedding <=> $1`) `Execution Time` | 3.0ms |
| 쿼리 벡터 리터럴 크기 | 약 39KB (파라미터 하나, SQL에서 세 번 참조) |
| 로컬(한국) → Neon `SELECT 1` 왕복 | 77ms |
| 로컬(한국) → Neon 앱 쿼리 왕복 | 237ms |
| `catalog_items` | 508행 (임베딩 있는 행 505), 16MB |

- **Vercel 함수는 `iad1`(미국 동부)에서 돈다.** 프로젝트 설정 `functionDefaultRegions: ['iad1']`, 배포 `regions: ['iad1']`로 확인했다. **DB는 Neon `ap-southeast-1`(싱가포르)**이다. 둘의 왕복 시간(RTT)은 약 200ms대다.
- Neon HTTP 드라이버는 쿼리 하나를 HTTPS 요청 하나로 보낸다. 연결이 새로 열리면 TCP·TLS 핸드셰이크를 하고, 39KB 본문을 올리는 데 여러 번 왕복한다(TCP 초기 전송창이 약 14KB). 이 왕복 5~7회에 RTT 200ms를 곱하면 관측된 1.1~1.9초와 맞는다.
- HNSW 인덱스는 어느 쿼리에서도 쓰이지 않는다. 500행에서는 플래너가 Seq Scan을 고르고, 그래도 3~8ms다. **이 규모에서는 인덱스가 문제가 아니다.** 원래 가설 1·2(벡터 인라인, 인덱스 미사용)는 서버 시간 기준으로는 기각이다. 벡터 크기는 전송 왕복 수에만 영향을 준다.
- 같은 거리 문제는 `/api/mcp` 요청 안의 다른 DB 호출(세션·인증·감사 로그)과 OpenAI 호출에도 똑같이 붙는다.

재현 스크립트는 커밋하지 않았다. 요지는 다음과 같다. `@neondatabase/serverless`의 `sql.transaction([...], { readOnly: true })` 안에서 기존 항목의 임베딩을 쿼리 벡터로 쓰고, 위 SELECT를 `EXPLAIN (ANALYZE, BUFFERS)`로 돌렸다.

## 처음 세운 가설 (기록용)

`catalog_items`는 약 405행이다. 인덱스를 전혀 타지 않고 전체를 훑어도 수십 ms면 끝나야 하는 규모인데, 1.1~1.9초가 걸린다. 코드에서 보이는 후보는 다음 셋이다.

1. **쿼리 벡터가 SQL 텍스트에 여러 번 인라인된다.** `cosineDistance(catalogItems.embedding, queryEmbedding)`가 WHERE 게이트(`vectorSimilarity`)와 SELECT·ORDER BY(`similarity`)에 각각 들어간다. 3072차원 float 리터럴 하나가 수십 KB라서, 이것이 여러 번 Neon HTTP 요청 본문에 실리고 서버에서 파싱된다.
2. **ORDER BY가 보너스를 더한 식이라 HNSW 인덱스를 못 탄다.** 거리 연산자로 정렬하지 않으므로 전체 스캔을 하고, 행마다 코사인을 2~3번 계산한다.
3. **Neon HTTP 왕복과 컴퓨트 상태.** 함수 리전과 DB 리전 사이의 거리나 콜드 컴퓨트 여부다.

결과는 위 EXPLAIN 절과 같다. 3번(리전 간 네트워크)이 맞았다.

## 반복률 측정은 보류

계획한 `mcp_audit_logs` 반복률 측정은 하지 않았다. 캐시 외부화가 본선에서 내려갔기 때문이다. 이후 임베딩 쪽을 다시 다룰 때 잰다.
