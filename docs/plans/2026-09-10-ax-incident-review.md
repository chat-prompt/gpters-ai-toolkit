# AX 문제 후보·검토·조치 관리

## 현재 상태

2026-09-10: 갱신 상태 개선은 PR #126, 운영 커밋 `15a5abe155ab41babfa1ef02e046160bb66e718d`로 배포했다. Vercel 성공과 운영 화면의 ‘화면 갱신’ 표시를 확인했다.

이 문서의 문제 검토 기능은 별도 브랜치 `feat/ax-incident-review`의 로컬 구현이다. 운영 DB 적용·운영 활성화는 아직 하지 않았다. AITK 패키지나 수집기를 변경하지 않는다.

## 구현한 흐름

- 기존 비공개 SQLite 사고 검토 도구의 판정 원칙을 TypeScript로 옮겼다. 기존 원장을 자동 복사하거나 과거 판정을 변경하지 않는다.
- 기존 AX 작업 이벤트에서 에이전트·소스·실패 단계·근거 종류별 후보를 만든다. 업무 유형은 미분류이며 같은 원인을 확정한 그룹이 아니다.
- 관리자는 검토 중, 사고 확정, 오탐 판정을 이유·비공개 근거 참조와 함께 기록한다. 수정에는 실제 적용 시각, 변경·롤백 참조와 수정 전 실패 표본이 필요하다.
- 재검증은 같은 소스·단계·근거의 수정 후 시도를 서버에서 다시 집계한다. 기본 최소 표본 10회. 실패·미종료·잘린 조회·원천 부재·기간 누락은 승인을 막는다. 실패와 성공이 같은 시도에 있으면 실패로 센다.
- ‘재검증 완료’는 관리자가 해당 관측 기간을 승인했다는 뜻이다. 독립적인 전송 확인이나 전체 업무 정상, 영구 해결, 변경의 인과 효과를 뜻하지 않는다. 화면은 승인 당시 표본을 보존한다.
- 새 실패는 재발 후보로 표시한다. 조회만으로 저장 상태를 바꾸지 않으며, 다음 관리자 판정에 재발 관측과 판단을 함께 기록한다. 새로 도착한 수정 전 실패는 수정된 사례를 다시 열지 않는다.
- 검토를 저장한 사례는 기간이 지나도 남는다. 아직 저장하지 않은 후보는 현재 작업 조회 범위에 한정된다. 후보는 스케줄러가 백그라운드에서 영구 적재하는 사고 로그가 아니다.

## 저장·접근 경계

`0040_ax_incident_reviews.sql`은 새 테이블 하나만 추가한다. 한 레코드에 상태·수정·승인 표본·검토 이력을 함께 저장한다. revision 조건부 갱신 및 생성 충돌 검사로 동시 판정의 덮어쓰기를 막는다.

조회와 저장 모두 내부 조직 관리자에게만 허용한다. 저장에는 실제 로그인 사용자 ID가 필요하며 개발용 AX 보기 우회만으로는 저장 권한이 생기지 않는다. 쿠키 인증 쓰기는 같은 origin의 JSON 요청만 허용하고, 입력 크기를 제한한다. 사용자 입력의 actor·관측 숫자·후보 생성은 받지 않고 서버 자료로 재구성한다. 인증정보·업무 원문은 저장하지 않으며 비공개 근거는 참조 문자열로만 기록하고 자동으로 열지 않는다.

운영 활성화 스위치는 `AX_INCIDENT_REVIEW_ENABLED=true`다. 기본값에서는 저장 API가 닫혀 있다. 운영 적용 전 복구 지점 및 DB 브랜치를 확인하고 0040 적용·스키마 대조·내부 관리자 접근을 검증한 후 활성화한다. 기존 SQLite 원장의 이관은 별도 검토가 필요하다.

## 검증

- 웹 단위 테스트 전체: 125개 파일, 2,699개 통과. 일회용 PostgreSQL 테스트 1개는 기본 실행에서 제외한다. 이후 추가한 폼 검증 2개를 포함한 관련 22개 테스트 통과.
- 인증 없음, 외부 조직 관리자, 일반 구성원, 다른 origin, 검토자 사칭, 잘못된 요청·과대 입력·저장소 비활성 상태를 차단했다.
- 후보 중복·단계/근거 구분·수정 전 기준선·누락/잘림/실패/미종료/표본 부족·시도 중복·시간 경계·재발·승인 표본 보존을 검증했다.
- 일회용 로컬 PostgreSQL에 0040만 적용하여 동시 생성 두 건 중 한 건만 저장, 오래된 revision 거부, 연결을 끊었다가 다시 조회한 후 이력 보존을 확인했다. 기존 로컬 DB와 운영 DB는 변경하지 않았다.
- 브라우저에서 후보 확정 → 수정 기록 → 표본 부족 승인 차단 → 성공 표본 10회 추가 → 재검증 완료를 확인했다. 데스크톱 밝은/어두운 테마와 390px 화면에서 겹침·가로 넘침을 확인했다.
- 앱 소스 타입 검사와 변경된 UI/API ESLint 통과. 운영·공유 DB에 API/E2E 전체 테스트를 실행하지 않았다.

격리 저장 검증은 로컬 PostgreSQL에 전용 DB를 새로 만들고 0040을 적용한 후 아래 명령으로 실행한다. 테스트 시작 시 DB 이름과 레코드 0건을 확인한다.

```sh
RUN_ISOLATED_INCIDENT_TESTS=true \
TEST_DATABASE_URL=postgresql://gpters:gpters_local_only@127.0.0.1:55432/ax_incident_test_20260910 \
DATABASE_DRIVER=postgres-js \
pnpm --filter @gpters/web exec vitest run tests/unit/ax-incident-store.postgres.test.ts
```

## 로컬 확인과 다음 범위

개발 화면: `http://127.0.0.1:3018/en/ax-preview-local`의 ‘문제 검토’. 해당 미리보기는 Git에서 제외한 합성 데이터이며 판정은 브라우저 저장소에만 남긴다. 서버 코드의 PostgreSQL 보존과 인증 경계는 별도 테스트로 검증했다. ‘테스트 초기화’로 합성 기록을 초기화할 수 있다. 개발 서버는 검수 후에도 유지한다.

다음 운영 단계는 DB 적용·권한 대조·활성화 후 실제 후보 한 건의 근거와 저장 결과를 대조하는 것이다. 이후 예약/프로세스/전달 영수증 자동 연결, 중앙 후보의 주기 적재, 알림·감시자 생존, 업무 유형별 비교 및 장기 이력 페이지네이션을 확장한다. 수집기 정상이나 단순 프로세스 종료를 전달 성공으로 바꾸지 않는다.
