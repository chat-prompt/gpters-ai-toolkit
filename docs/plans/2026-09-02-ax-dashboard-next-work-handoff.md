## 3. 숫자의 정확한 의미

- 검색 노출은 사용으로 보지 않는다.
- 로드는 스킬 지침을 불러온 신호이며 실제 적용과 다르다.
- 실제 사용은 명시적인 `apply` 보고를 기준으로 한다.
- `로드 후 적용`은 같은 사용자·흐름(journey, 없으면 session)·스킬의 앞선 로드와 연결할 수 있는 적용이다.
  일별 잔디·흐름 차트에서는 **로드 코호트 단위로 로드 날짜에 귀속**하고 코호트당 한 번만 센다.
  적용 날짜 기준 이벤트 수로 세면 기간 전 로드·반복 적용 때문에 전환율 분자가 분모를 넘을 수 있어 2026-09-02 교차 리뷰에서 바꿨다.
- `연결 가능 로드`는 위 코호트 중 flow ID와 user ID가 모두 있는 것이다. 전환율 분모는 전체 로드가 아니라 이 값이다.
- `로드 없이 적용`에는 서버 호출 없이 로컬에 저장된 스킬을 재사용한 경우 등이 포함될 수 있다.
- 세션 ID 없는 과거 CLI 로드는 적용과 정확히 연결할 수 없으므로 전체 로드 수에는 포함하되 전환율 분모에는 주의한다.
- 에이전트 thinking 토큰이 output에 포함되는지는 `thinkingTokensRelation`을 따른다. `included-in-output`이면 총량에 다시 더하지 않는다.
- 사람과 에이전트는 같은 활성 인원 지표에 합치지 않는다.
- **재사용은 같은 사용자가 같은 스킬을 서로 다른 날(UTC 날짜)에 2일 이상 적용한 것이다** (2026-09-04 확정).
  - 흐름(journey) 기준으로 셀 수 없다. 30일 적용 208건 중 흐름 ID가 있는 것은 25건뿐이다.
  - 이벤트 수 기준도 쓰지 않는다. 한 작업이 1초 간격으로 두 번 보고된 사례가 있어 중복 보고를 재사용으로 센다.
  - 날짜 단위는 **같은 날 여러 번 쓴 경우를 놓치는 보수적인 정의**다. 그래도 이쪽을 택했다 —
    하루에 몰아 쓰고 다시 안 돌아오는 것은 정착이 아니고, 날을 바꿔 다시 여는 것이 정착의 신호이기 때문이다.
  - 팀의 aitk 버전이 통일돼 흐름 ID가 붙기 시작하면 흐름 기준 재사용도 함께 볼 수 있다. 그때 이 정의를 재검토한다.
- 신규/재사용자는 **전 기간 최초 적용 시각**으로 가른다. 관측 시작(2026-06-15)을 화면에 적어,
  긴 기간에서 "신규만 있고 재사용자 0"이 나오는 이유가 보이게 한다.

### P1. 스킬 개선 기회 자동 분류 — 2026-09-04 구현 완료 (§14)

아래 여섯 중 1·2·5와 "한 사람만 쓰고 있음"을 구현했다. 4(검색 결과 0건)는 건수만 보여준다.
6(실패·중단)은 실행 보고 표본이 30일 15건이라 아직 분류로 세우지 않았다.

기존 데이터로 다음 분류를 만든다.

1. 검색은 많고 로드가 적음 → 제목·설명·검색 키워드 개선
2. 로드는 많고 적용이 적음 → 지침·예시·품질 개선
3. 적용은 많고 사용자가 적음 → 사내 확산 후보
4. 검색 결과 0건 → 신규 스킬 후보
5. 결과 미보고가 많음 → 계측 개선 또는 판단 보류
6. 실패·중단이 많음 → 실행 안정성 개선

초기에는 복잡한 종합 점수 하나보다 분류별 목록과 근거 수치를 우선한다.

## 10. 에이전트 텔레메트리 수집기 운영 (2026-09-03)

에이전트 활동 패널의 스킬 로드는 각 에이전트 호스트에 설치된 AITK 수집기가 보낸 값이다. 소스마다 관측 범위가
다르므로 `SOURCE_INFO`(`packages/lib/src/features/ax/agent-activity.ts`)의 capabilities로 "미관측"과 "0건"을 구분한다.

- **Hermes(뽀케터)**: `skill_view(name, file_path?)` 호출을 스킬 로드로 센다. 도구 인자를 읽지 않는 프라이버시 원칙의
  유일한 예외가 스킬 이름이며, `file_path`가 있으면 링크 파일 열람이라 세지 않는다. 스킬 이름은 서버 계약

  스킬 신호를 관측한 것으로 판정한다.
- **Codex**: 스킬 로드 신호가 아직 없다. capabilities에서 `skills: false`.
- **수집 주기**: 기본 1시간(`--interval 3600`). 사람의 `aitk usage report`는 별도로 하루 한 번이다. 노트북에서 도는
  에이전트만 `--interval 21600`. 대시보드의 stale 판정은 `max(12시간, 2 × interval)`이라 1시간 설정에서도 12시간이다.
- **CLI 업그레이드 함정**: `install`이 설치 당시 실행 파일(`share/gpters-aitk/<version>/aitk.js`)을 설치 기록과
  launchd plist에 고정한다. `install-from-repo.sh`는 `aitk` 래퍼만 바꾸므로 **새 버전을 깔아도 예약 수집은 옛
  바이너리로 돈다.** 배포 뒤에는 반드시
  `aitk agent-telemetry upgrade --agent <id> --source <source>`까지 실행하고,
  `doctor`의 `cliUpToDate`와 서버 배치의 `runtime.collectorVersion`으로 확인한다.
- **뽀케터에게 작업을 요청할 때**: Slack DM(`D0BNWKWKXTM`)에서 원문은 한 줄, 상세는 스레드. 승인 커밋 전체 SHA를
  주고 임시 clone에서만 작업하게 한다. 호스트에 Bun이 없어 빌드는 `corepack pnpm dlx bun`으로 돈다. 명령 실행
  승인(특히 `rm -rf`)은 사용자가 직접 눌러야 한다.
- **dry-run으로 과거 구간을 보려면** 빈 `--checkpoint-dir`을 지정해야 한다. 운영 checkpoint는 delta + seen 해시라
  마지막 수집 이후만 새로 본다.
- **늦게 기록된 결과**: 스킬 로드는 결과 행이 도착해야 확정하는데 수집 창은 앞으로만 움직인다. 0.7.8부터
  결과를 기다리는 호출을 checkpoint(`hermesPendingSkillCalls`)에 들고 다니다가 결과를 만나면 그때 센다.
  7일이 지나면 버린다.

- **`skip`에는 자동 스킵(`context LIKE 'auto:%'`)과 검색 결과 거절(`query IS NOT NULL`)이 섞여 있다.**

## 16. 수집기가 실행할 node 고정 (2026-09-04, PR #81)

뽀둥이 수집기를 재지정하다 **예약 수집이 어느 node로 도는지를 아무도 의도하지 않은 채 정해버리는**
구조가 드러났다. 네 가지가 같은 뿌리였고 함께 고쳤다.

원인:

- `renderLaunchdPlist`는 node를 절대 경로로 `ProgramArguments[0]`에 넣고 `EnvironmentVariables`에
  PATH가 없다 — **폴백이 없다**
- `upgrade`가 그 값을 `process.execPath`(실행 셸의 node)에서 가져온다
- `install-from-repo.sh`가 만드는 래퍼가 `exec node`라 PATH의 node를 쓴다
  → **어떤 셸에서 `aitk`를 부르느냐가 그대로 예약 수집의 node가 된다.** 실제로 Hermes 런타임 셸에서
  돌려 `~/.hermes/node/bin/node`가 박혔고, 그 런타임이 정리되면 수집이 조용히 멈추는 상태였다

고친 것:

- 래퍼가 `exec`할 node를 설치 시점에 절대 경로로 고정한다(`install-from-repo.sh --node <path>`)
- `agent-telemetry install`·`upgrade`·`doctor`에 `--node-path`를 열었다. **명시하면 철자 그대로**
  비교·저장한다 — `samePath`가 realpath로 보는 바람에 심링크 → Cellar 재지정이 no-op이 되던 것도 함께 고쳤다
- `doctor`의 `cliUpToDate`에서 **node 비교를 뺐다.** 점검을 어떤 node로 실행했는지는 설치의 건강과
  무관한데, 포함하면 래퍼로 doctor를 돌렸다는 이유만으로 정상 수집기가 `ok: false`로 보였다.
  기록된 node의 존재는 `cliExists`가, 무엇이 박혔는지는 신규 `scheduledNodePath`가 보여준다

**앞으로 호스트에 upgrade를 시킬 때는 `--node-path`로 어느 node를 쓸지 지정한다.**
Homebrew라면 `/opt/homebrew/opt/node@24/bin/node`(심링크)가 `Cellar/node@24/<버전>/`(버전 고정)보다 오래간다.
