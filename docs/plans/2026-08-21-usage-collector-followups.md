# 사용량 수집기(`apps/aitk-cli/src/usage/`) 후속 과제

2026-08-20에 이 모듈로 Deletion Test를 돌렸다 — 구현 448줄을 지우고 사양·테스트만으로 재생성한 뒤,
실제 로컬 세션 데이터에 돌려 원본과 답을 대조했다. 그 과정에서 출력 토큰 과소집계 버그를 찾아 고쳤고(#30),
**함께 드러났지만 아직 처리하지 않은 항목 3건**을 여기에 남긴다.

셋 다 지금 당장 숫자가 틀리는 문제는 아니다. 다만 전부 "코드에만 있고 어디에도 적혀 있지 않은 결정"이라,
다음에 이 파일을 건드리는 사람(또는 에이전트)이 모르고 바꾸면 조용히 동작이 달라진다.

## 1. 집계 구간 끝 경계를 사양에 명시하고 테스트로 고정

**현재 동작** — 양끝을 모두 포함하는 **닫힌 구간** `[start, end]`이다.

- `apps/aitk-cli/src/usage/claude-code.ts:132` — `if (!Number.isFinite(at) || at < startMs || at > endMs) return`
- `apps/aitk-cli/src/usage/codex.ts:149` — 동일

**왜 문제인가** — 이게 의도된 선택인지 우연인지 어디에도 적혀 있지 않다. Deletion Test에서 재생성한 두
구현이 **둘 다 독립적으로 반열린 구간 `[start, end)`을 골랐다.** 즉 사양만 보면 반열림이 더 자연스럽게
읽힌다는 뜻이다. 테스트도 골든(실데이터 대조)도 이 차이를 잡지 못했다 — 경계에 정확히 걸치는 데이터가
없었기 때문이다.

지금은 호출부가 UTC 하루 경계로 스냅해서 넘기므로(`6f0c615f`) 실제로 부딪히지 않지만, 구간을 잘라
합산하는 집계를 만들면 경계 레코드가 두 번 세어진다.

**할 일**

1. 어느 쪽을 정답으로 삼을지 정한다. **반열린 구간 `[start, end)`을 권한다** — 구간을 이어 붙일 때
   중복이 생기지 않고, 재생성본 두 개가 모두 그렇게 읽은 쪽이다. 다만 바꾸면 경계에 걸친 레코드 하나가
   빠지므로, 호출부가 UTC 하루 경계를 넘기는 지금 조건에서 집계값이 변하지 않는지 먼저 확인할 것
2. 정한 규칙을 `apps/aitk-cli/src/usage/types.ts`의 `UsageWindow` TSDoc에 한 줄로 적는다
3. `tests/usage/collectors.test.ts`에 `timestamp === window.end`인 레코드를 넣어 포함/제외를 못박는다
   (Claude Code·Codex 양쪽)

**완료 기준** — 경계 레코드를 하나 넣은 테스트가 있고, 그 테스트가 반대 규칙으로 바꾸면 실패한다.

## 2. `jsonl.ts` 사전 필터의 성능 주장 정정 또는 벤치마크 추가

**현재 주석** (`apps/aitk-cli/src/usage/jsonl.ts:4`)

> `~/.claude/projects`는 GB 단위로 자란다. 전부 파싱하면 명령 하나가 분 단위로 늘어지므로 두 단계로 거른다.

**측정 결과** — 재생성본 두 개가 모두 이 최적화를 버렸길래 실제 비용을 쟀다. 로컬 실데이터
(측정 시점 약 237MB → 이후 350MB대) 기준으로 **사전 필터가 있든 없든 차이를 검출하지 못했다.**
세 번 측정했고 셋의 차이가 매번 실행 간 편차(±0.03초) 안에 들어갔다.

주의: 이건 "효과가 0"이라는 증명이 아니라 **이 데이터 크기에서는 검출되지 않는다**는 뜻이다.
다만 주석이 주장하는 "분 단위"는 확실히 아니다.

**할 일** — 둘 중 하나.

- (a) 주석에서 검증되지 않은 수치 주장("분 단위")을 빼고, 실제로 관측된 근거만 남긴다
- (b) 최적화를 유지할 근거가 필요하면 재현 가능한 벤치마크를 레포에 넣는다.
  GB급 합성 트랜스크립트를 만들어 사전 필터 유무를 비교하는 스크립트면 충분하다

**완료 기준** — 주석의 모든 수치 주장이 레포 안의 재현 가능한 근거를 가리키거나, 주장 자체가 사라진다.

## 3. 스트리밍 응답이 구간 경계에 걸칠 때 인접 구간 합이 부푸는 문제

**무엇인가** — 같은 `message.id`가 스트리밍 중 여러 줄로 기록되는데(#30 참고), 시간 필터가 중복 판정보다
**먼저** 적용되고 중복 판정용 Map은 호출마다 초기화된다 (`claude-code.ts:132`가 `:155`보다 앞).

미완성 줄과 완료 줄이 서로 다른 구간에 떨어지면 이렇게 된다.

```
구간 A: 미완성 줄만 보임  → output 2   를 센다
구간 B: 완료 줄만 보임    → output 676 을 센다
A + B = 678             실제 응답은 676
```

**지금 영향이 없는 이유** — 서버가 클라이언트별로 **최신 보고 하나만** 사용하기 때문에
(`packages/lib/src/features/ax/usage.ts`), 인접 구간을 더하는 경로가 현재 없다.

**언제 문제가 되나** — 일별/주별 집계를 구간별로 쌓아 합산하는 기능을 만들 때. 그때 이 항목을 먼저 해결할 것.

**할 일** (그런 기능을 만들 때)

1. 응답 단위 귀속 규칙을 정한다 — 완료 줄이 속한 구간에 응답 전체를 넣는 쪽이 자연스럽다
2. 그러려면 구간 필터를 중복 판정 **뒤로** 옮겨야 한다. 다만 그 순서로 바꾸면 구간 밖 파일까지 파싱하게
   되므로, mtime 기반 파일 스킵(`findJsonlFiles`)과의 상호작용을 같이 봐야 한다
3. 인접 두 구간의 합이 전체 구간 한 번 집계와 같은지 확인하는 테스트를 추가한다

**완료 기준** — 구간을 둘로 쪼개 각각 집계한 합이, 같은 범위를 한 번에 집계한 값과 일치한다.

## 이 파일을 건드릴 때 알아두면 좋은 것

Deletion Test에서 얻은 교훈이라 함께 남긴다.

- **손으로 만든 픽스처는 우리가 상상한 모양만 담는다.** 기존 중복 제거 테스트는 *완전히 동일한 두 줄*을
  픽스처로 썼는데, 실제 데이터의 중복은 값이 다른 줄이었다. 그래서 테스트 47개가 전부 초록불인 채로
  출력 토큰이 32.5% 어긋날 수 있었다. 이 모듈을 고칠 땐 **실제 `~/.claude/projects` 데이터에 돌려
  집계값을 대조**하는 단계를 넣는 게 안전하다 (대화 내용은 읽지 말고 `usage`·`stop_reason` 필드만 볼 것)
- 같은 `message.id`의 여러 줄을 다룰 땐 **줄 단위로 통째 채택**해야 한다. 필드별로 최댓값을 따로 취하면
  어느 줄에도 존재하지 않는 조합이 만들어지고, 증분을 각 줄의 모델에 귀속시키면 한 응답의 토큰이 두 모델로
  쪼개진다. 둘 다 #30의 중간 구현에서 실제로 발생했고 교차 검토로 잡았다
- Claude Code와 Codex는 캐시 토큰 규칙이 **서로 반대**다. Claude Code는 `input_tokens`에 캐시가
  포함되지 않아 `cache_creation`을 더하고, Codex는 `input_tokens`가 `cached_input_tokens`를 포함해
  빼야 한다. 한쪽을 고칠 때 다른 쪽에 같은 논리를 복사하지 말 것
