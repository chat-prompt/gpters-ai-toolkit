## 2. 공통 합의 사항 (5/5 동의)

### 아키텍처 설계는 건전하다
- 역할 분담 원칙 ("복리엔진은 실습을 모른다")이 명확
- REST vs MCP 선택 근거 타당
- Graceful degradation 설계가 탄탄
- 단계적 통합(Phase 1/2/3)이 현실적

### MVP 먼저 해야 한다 (5/5 강력 지지)
- 전용 REST API 전에 **기존 semantic_search 재사용 + 하드코딩 10개로 3일 검증**
- 가치가 확인되면 그때 전용 API 설계
- 기획자: "풀 구현 전에 반드시 이 단계를 거쳐야 한다"
- 복리엔진 개발자: "복리엔진 측 변경량이 0에 가까움"

### Phase 2/3은 보류
- Rona 개발자: "복리엔진 가용성 실적 3개월 축적 후 재논의"
- 기획자: "도구 지식 허브로의 확장은 별도 전략적 의사결정"
- 복리엔진 사용자: "이관 자체가 품질 개선은 아님"

## 3. 관점별 고유 인사이트

### Rona 개발자만 지적한 것
| 이슈 | 심각도 | 상세 |
|------|--------|------|
| `Promise.race` → `AbortController` 필요 | 🔴 | 타임아웃 후 좀비 fetch 누적 위험. `enrich-tool-docs.ts` 기존 패턴도 AbortController 사용 |
| `buildSkillDocsMessage()` 인터페이스 미정의 | 🟡 | Rona 측 구현의 70%를 차지하는 핵심 함수인데 계약서 없음 |
| `toolDocsContext` 현재 동작 검증 필요 | 🔴 | undefined인 이유가 "미구현"인지 "의도적"인지에 따라 사이드이펙트 상이 |
| Rona 공수 과소추정 | 🟡 | 문서: 1일 → 현실 추정: 3.5일 (3.5배) |
| Phase 2/3 이관 시 "이중 운영 기간(dual-run)" 필요 | 🟡 | 자체 싱크 제거 전 2주간 결과 비교 기간 |

### 복리엔진 개발자만 지적한 것
| 이슈 | 심각도 | 상세 |
|------|--------|------|
| `whyRelevant`/`suggestedStep`은 LLM 생성 필드 | 🔴 | 시맨틱 검색만으로 생성 불가 → REST 내 LLM 호출 필요 → 응답 10초+ → 5초 타임아웃에 걸림 |
| CLI 25개를 `catalog_items`에 넣으면 임베딩 검색 오염 | 🔴 | description이 짧아 벡터 빈약 + 기존 스킬과 타입 혼동 |
| Phase 1을 1a/1b로 분리 제안 | 🟡 | 1a: REST + 스킬 검색만 (1주), 1b: MCP/CLI 시드 (1주) |
| `content` 전문 포함 시 payload 25KB+ | 🟡 | 스킬 5개 × 5KB = 불필요한 전송량 |

### 기획자만 지적한 것
| 이슈 | 심각도 | 상세 |
|------|--------|------|
| 3/21 Go/No-go 전 리소스 분산 금지 | 🔴 | 11일 남은 상태에서 2주짜리 새 프로젝트 시작하면 양쪽 다 실패 |

### Rona 사용자만 지적한 것
| 이슈 | 심각도 | 상세 |
|------|--------|------|
| MCP 가이드 — 초급자가 따라할 수 있는가? | 🔴 | beginner에게 "MCP 서버 연결하세요"는 당혹. level 기반 필터링 필요 |

| MCP 연결 실패 시 대안 경로 없음 | 🟡 | `fallbackApproach` 필드 추가 제안 |
| 노출 UX 가이드라인이 문서에 없음 | 🟡 | API 설계만 있고 "학습자에게 어떻게 보여줄지"는 Rona에 위임 — 최소 원칙 명시 필요 |

### 복리엔진 사용자만 지적한 것
| 이슈 | 심각도 | 상세 |
|------|--------|------|
| CLI 도구가 기존 MCP semantic_search에 혼입 위험 | 🔴 | `type NOT IN ('cli-tool')` 기본 필터 필요 |
| 낮은 적중률이 Rona에 노출되면 복리엔진 브랜드 역효과 | 🟡 | MVP에서 적중률 사전 측정 필수 |
| stale 감지를 사용자에게 가시화해야 가치 | 🟡 | 내부 플래그만으론 사용자가 모름 → "⚠️ 구버전 참조 포함" 표시 |
| MCP 시드 수동 큐레이션 → 자동 싱크가 동시에 나와야 | 🟢 | 수동 시드만으로는 금방 stale |

## 7. 최종 판정

### **Conditional Go — MVP 우선, 본격 착수는 3/21 이후**

이 아키텍처는 **문제 정의, 역할 분담 원칙, 시스템 설계 모두 건전**합니다.
5명 전원이 아키텍처 자체에는 동의했습니다.

그러나 **지금 바로 Phase 1 풀 구현에 착수하는 것은 No-go**입니다.
이유:
1. 복리엔진 3/21 Go/No-go 판정까지 11일 — 리소스 분산 금지
2. 응답 구조에 LLM 생성 필드가 포함되어 기술적 실현 불가능
3. CLI 도구 저장 방식이 기존 검색 품질을 훼손할 위험
4. 실습 대상 적중률 미검증

**권장 경로:**
```
3/10~3/12  MVP 3일 검증 (적중률 측정 + 하드코딩 품질 평가)
3/21       Go/No-go 최종 판정
3/24~      Go이면 → 수정된 Phase 1 착수 (단순화된 응답, 별도 CLI 테이블)
           No-go이면 → Rona 연동 보류, 복리엔진 존속 결정 우선
```
