# 이모지 문제 보고의 접수 경계

## 범위

기존 텍스트 보고 요청에 선택적으로 이모지 보고 요청을 추가한다. 반응을 붙인 정확한 메시지·반응자·이벤트 ID를 잃지 않고 저장하되, 최종 판정은 지정된 사람이 수행한다. 범용 API·정규화 함수·화면을 구현했으며 실제 런타임 설치나 운영 이모지 활성화는 별도 파일럿 단계다.

이 저장소에는 익명 코드·계약만 기록한다. 내부 대화, 운영 호스트, 실제 반응자 ID와 사례는 비공개 운영 기록에 둔다.

## 구현

- 원본 메시지와 스레드 루트를 별도 필드로 보존한다. 링크는 원본 메시지 시각에 반드시 일치해야 한다.
- 활성화 스위치와 팀·채널·반응자·이모지 허용 목록을 모두 요구한다. 기본값은 거부다.
- `captureSlackReaction`은 인증된 어댑터에서 받은 필드만 정규화한다. 봇·비활성·비허용 반응·삭제 이벤트는 접수 요청으로 반환하지 않는다. 문맥 누락을 모델 추론으로 메우지 않는다.
- 보고는 `reaction-requested`로 구분하고 가짜 텍스트 승인 링크를 받지 않는다. 화면은 에이전트가 전달한 반응 정보임을 표시한다.
- DB의 기존 문제 키·revision 원장을 재사용한다. 다른 이벤트를 같은 메시지에 재접수해도 별도 사례를 만들지 않으며, 변경된 본문은 409로 돌려보낸다. 사람의 판정을 반응으로 뒤집지 않는다.
- DM 요약의 공유 승인과 원문 접근권을 별도로 다룬다. 개인 기록 트리거를 조직 전체 공유 승인으로 확대하지 않는다.

## 검증 및 제한

웹 단위 테스트 130개 파일에서 2,730개 테스트를 통과했다(격리 DB 전용 2개 제외). 앱 소스·헬퍼 타입 검사, 변경 파일 린트와 헬퍼 빌드를 통과했고, 합성 데이터로 로컬 데스크톱 밝은·어두운 테마 및 390px 화면을 확인했다. 운영 DB에 보고를 쓰는 테스트는 수행하지 않았다.

단위 테스트로 원본 답글 식별, 이벤트 순서, 누락 문맥, 다른 반응자·채널·팀, 봇/비활성, 기본 거부, HTTP 등록 경계, 기존 보고와의 호환, UI의 요청/승인 구분을 검증한다. 원문 Slack 이벤트 서명 검증과 사용자 프로필 확인은 실제 어댑터 책임이며, 서버는 에이전트가 전달한 정보로 저장한다.

진행 순서는 대시보드 구현·배포, 에이전트 운영자에게 프로토콜 전달, 별도로 요청된 합성 시나리오의 런타임 연결이다. 문서 전달은 이모지 사용·설치·실제 보고 실행 요청이 아니다. 기존 노트 자동화를 수정하거나 중복으로 기록하지 않도록 목적지·공유 범위·오류 회신을 확정하고, 반응 추가·삭제·재추가와 승인되지 않은 반응자를 검증한다. 자동 재시도 워커·Slack 푸시·기존 기록 이관은 이번 구현에 포함하지 않는다.
