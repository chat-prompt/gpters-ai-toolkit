# Claude Code 검색 쪽지·강제 훅 작업 이어받기 (2026-10-29)

Claude Code 세션의 마지막 실행기와 로그를 확인하고, 그 세션에서 사용한 쪽지·강제 훅 문구와 함께 불러오는 스킬 안내를 저장소에 그대로 반영했다. 모델이나 실험 조건을 바꿔 재실행하지 않았다. 운영 배포·DB 변경은 하지 않았다.

## 1. 이어받은 상태

앞선 Claude Code 세션은 작업 쌍 10개를 3회씩, 두 조건(쪽지만 / 쪽지+강제 훅)으로 실행했다. 총 60세션이며 각 세션에 첫 작업 → 후속 → 다른 작업 순서로 메시지를 3개씩 보냈다. 실행기는 `gate1029/run.sh`, 집계기는 `gate1029/score.py`·`tally.py`다.

- 모델 설정: `--model sonnet`.
- 턴 제한: `--max-turns 6`.
- 세션마다 같은 폴더를 쓰고 2·3번째 메시지는 `--resume`으로 연결.
- 실제 aitk 실행과 지정한 외부 쓰기 도구는 차단하고, 검색을 시도한 도구 호출을 집계.
- 두 조건 모두 같은 새 쪽지 원문 사용. 강제 훅 활성화 여부만 다름.

## 2. 기존 표를 그대로 재집계한 결과

숫자는 **검색 시도가 관찰된 메시지 수 / 전체 30건**이다. 아래 표는 원래 집계기를 그대로 다시 실행해 확인한 값이며, 정상 완료율을 나타내지 않는다.

| 메시지 | 쪽지만 | 쪽지 + 강제 훅 |
|---|---:|---:|
| 첫 작업 | 19/30 | 27/30 |
| 후속(“좋아, 그대로 계속 진행해줘”) | 0/30 | 3/30 |
| 다른 작업으로 바뀐 요청 | 9/30 | 16/30 |

## 3. 이어받으며 발견한 오류 — 최종 효과로 확정하면 안 됨

180개 로그의 마지막 `result`를 확인한 결과 **정상 완료 142개, 사용량 제한 31개, 턴 제한 7개**였다. 사용량 제한 31개는 `subtype: success`라도 `is_error: true`이고, 본문에는 `You've hit your 5-hour limit`가 있었다. 실행기가 종료됐다는 것과 실험 응답이 정상 완료됐다는 것은 다르다.

| 메시지 | 조건 | 정상 완료 | 사용량 제한 | 턴 제한 |
|---|---|---:|---:|---:|
| 첫 작업 | 쪽지만 | 23 | 5 | 2 |
| 첫 작업 | 쪽지 + 훅 | 25 | 4 | 1 |
| 후속 | 쪽지만 | 23 | 6 | 1 |
| 후속 | 쪽지 + 훅 | 24 | 5 | 1 |
| 작업 바뀜 | 쪽지만 | 23 | 6 | 1 |
| 작업 바뀜 | 쪽지 + 훅 | 24 | 5 | 1 |

원래 집계기는 결과 오류 여부를 구분하지 않는다. 검색 전에 오류로 중단된 메시지를 실제 검색 누락과 구분해서 봐야 한다. 또 같은 세션의 앞 메시지가 오류로 끝났다면 다음 메시지의 맥락도 원래 의도한 조건과 달라질 수 있다. 정상 완료 응답만 따로 세더라도 이 영향이 자동으로 해소되지는 않는다.

따라서 위 원집계 표만으로 강제 훅의 효과나 운영 적용 준비 완료를 확정하지 않는다. 이번에는 기존 모델·턴 제한·집계기를 바꾼 추가 실험을 하지 않았다.

### 3-1. 사용량 제한 세션을 뺀 재집계 (Claude Code, 같은 날)

사용량 제한은 모두 3회차(`*-3`) 세션에서 났다: off 6개(10·5·6·7·8·9), on 5개(10·6·7·8·9). 세 메시지 중 하나라도 사용량 제한에 걸린 세션을 통째로 빼고, 같은 `tally.py`로 다시 셌다.

| 메시지 | 쪽지만 (24세션) | 쪽지 + 강제 훅 (25세션) |
|---|---:|---:|
| 첫 작업 | 17/24 | 25/25 |
| 후속 | 0/24 | 3/25 |
| 다른 작업으로 바뀐 요청 | 9/24 | 16/25 |

턴 제한에 걸린 메시지는 조건·메시지마다 1개씩이다. 원집계에서 '도구 안 씀'으로 보인 누락은 대부분 사용량 제한이었다. 정상 세션만 봐도 훅이 있으면 첫 작업과 작업 바뀜에서 검색을 덜 놓친다. 세션 수가 24·25로 줄어든 표본이고, 같은 조건 반복 실험은 하지 않았다.

### 3-2. 2판: 실제 검색 + 쪽지 한 줄 + 5자 규칙 (Claude Code, 같은 날)

1판의 남은 누락을 보니 두 가지였다. 실험이 `aitk`를 막아서 앞 검색이 거부된 뒤 Claude가 다시 시도하지 않은 경우, 그리고 재료가 없어 되묻고 끝낸 경우다. 훅의 "10자 미만은 후속" 규칙이 "PR 설명 써줘"(9자)를 통과시킨 것도 찾았다.

바꾼 것:
- `skill-search.sh` 쪽지 두 곳에 "재료가 없어 되물어야 할 때도 묻기 전에 먼저 검색하세요. 맞는 스킬이 무엇을 물어야 할지 알려 줍니다." 추가.
- `skill-gate.sh` 짧은 메시지 기준 10자 → 5자. 테스트에 짧은 답(`sure`) 통과, 짧은 새 요청(`PR 설명 써줘`) 차단을 넣었다(`LC_ALL=C`에서도 통과).
- 실행기는 `aitk`를 막지 않고 로컬 aitk2 전용 shim(127.0.0.1:3100)을 PATH 앞에 두었다. 운영 MCP 서버(`mcp__plugin_gpters-ai-toolkit_gpters-ai-toolkit`, `mcp__gpters-ai-toolkit`)는 통째로 막았다.

1회차 20세션만 돌렸다(조건마다 10개). 사용량 제한 0건, 턴 제한 0건.

| 메시지 | 쪽지만 | 쪽지 + 강제 훅 |
|---|---:|---:|
| 첫 작업 | 검색 7/10 · 불러옴 5 | 검색 10/10 · 불러옴 7 |
| 후속 | 0/10 | 0/10 |
| 다른 작업으로 바뀐 요청 | 검색 8/10 · 불러옴 4 | 검색 10/10 · 불러옴 4 |

같은 1회차의 1판은 작업 바뀜이 3/10 → 7/10이었다. 되묻던 요청(슬라이드 개요, 실습 문제, 인스타 문구)은 두 조건 모두 묻기 전에 검색했다. 응답 시간 중간값은 실제 스킬을 읽느라 50~83초다. 표본이 작아 참고 수치로만 본다.

시간·토큰(중간값, 같은 2판 안에서 쪽지만 → 쪽지 + 훅):

| 메시지 | 시간 | 토큰(캐시 포함) |
|---|---|---|
| 첫 작업 | 64.5초 → 83초 (+18.5초) | 18.9만 → 21.5만 (+13%) |
| 후속 | 47.5초 → 42초 | 10.9만 → 12.0만 (+10%) |
| 작업 바뀜 | 54.5초 → 50초 | 18.1만 → 21.3만 (+17%) |

훅 때문에 늘어나는 시간은 첫 작업의 한 번 막힘(약 20초)이다. aitk 자체는 로컬 shim 기준 검색 1~2.5초, 불러오기 0.7초다. 1판(20초대)보다 전체가 길어진 것은 스킬 본문을 실제로 읽고 따르며 도구 호출이 늘었기 때문이다(첫 작업 도구 호출 중간값 2 → 3.5~4.5). 후속 메시지가 aitk 호출 없이도 17초 → 47초로 늘어난 원인은 이 데이터로 가르지 못했다(앞 메시지로 길어진 대화, 실행 시간대 차이로 추정).

## 4. 저장소 반영과 검증

실험 폴더 `gate1029/plugin/`의 아래 파일 3개를 그대로 옮겼다. 바꾸기 전 파일은 별도 임시 폴더에 보존했다.

- `apps/claude-code-plugin/scripts/skill-search.sh`: 같은 프로젝트의 새 결과물·명시적 팀 스킬 요청을 검색 대상으로 안내. 검색어는 “하려는 일 + 재료·대상”, 맥락 필수, 후보 5개.
- `apps/claude-code-plugin/scripts/skill-gate.sh`: 차단 시 안내도 같은 검색어·맥락·후보 수로 맞춤. 검색/후속 판정 로직은 원래 실험본 그대로.
- `apps/claude-code-plugin/skills/skill-suggest/SKILL.md`: 쪽지와 함께 읽는 안내도 실험본과 일치시킴.

복사 후 세 파일 모두 실험본과 바이트 단위로 같은지 확인했다. SHA-256은 다음과 같다.
