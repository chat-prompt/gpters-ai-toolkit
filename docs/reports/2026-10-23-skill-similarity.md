# 임베딩·유사도 계산 방식 실험 정리 (2026-10-21 ~ 10-23)

Linear DEV-4697(스킬 검색 개선)에서 유사도를 매기는 방식을 여러 가지로 바꿔 본 기록입니다. 두 가지를 다룹니다.

- **검색 점수** (DEV-4698): 검색어와 스킬이 얼마나 맞는지 매기는 점수
- **스킬끼리 유사도** (DEV-4699): 중복 스킬을 찾으려고 스킬과 스킬을 비교하는 점수

무엇을 바꿨고 바꾼 뒤 점수가 어떻게 달라졌는지를 주로 적었습니다. 모든 계산은 10/21에 운영에서 복사해 온 로컬 DB(게시된 516개)로 했습니다. 운영 DB에는 쓰지 않았습니다. 아래 변경은 아직 운영에 넣지 않았습니다.

이 문서에서 "유사도"는 두 글의 뜻이 얼마나 가까운지를 0~1 점수로 나타낸 것입니다. 글을 숫자 목록(임베딩)으로 바꾼 뒤 두 목록이 얼마나 닮았는지 계산합니다. 1에 가까울수록 비슷합니다. 글자가 같은지를 보는 점수는 아닙니다. 표현이 달라도 뜻이 같으면 점수가 높게 나옵니다.

## 요약 1. 검색 점수 (검색어 ↔ 스킬)

안재민의 Claude Code 세션에서 실제로 실행된 `aitk search` 검색 41개로 비교했습니다. 정답 스킬은 Claude와 Codex가 출처를 가린 후보를 따로 보고 둘 다 "바로 도움"이라고 한 것으로 정했습니다. 
(클로드와 gpt 두 ai를 judge로 활용해 두 agent의 의견이 일치한 스킬만 정답으로 선정하였습니다.)
검색 결과 1위가 정답인 개수를 셉니다. 만든 방법은 0절에 있습니다.

| 바꾼 것 | 바꾸기 전 | 바꾼 뒤 | 1위 정답 (41개 중) |
| -- | -- | -- | -- |
| **스킬 임베딩에서 본문을 뺌** | 이름·설명·태그·본문을 모두 넣어 임베딩 | 이름·설명·태그만 넣어 임베딩 | 19 → **30** (3위 안: 32 → 38) |
| **글자가 겹치면 주던 가산점을 없앰** | 검색어 전체가 이름 안에 있으면 +0.15, 설명 안에 있으면 +0.10, 태그 안에 있으면 +0.05 | 없음 | 운영 방식은 검색어 전체가 들어 있어야 해서 거의 붙지 않았습니다. 단어별 태그 가산점을 따로 시험했더니 26으로 오히려 줄었습니다 |
| **검색어에 스킬 ID나 이름이 그대로 있으면 +0.3, 무조건 1위** | 없음 | +0.3을 더하고 순서는 맨 앞에 둡니다. 최소 유사도보다 낮아도 결과에 넣습니다 | 30 → **32** |
| (참고) ax-workflow 설명 채움 | 설명이 비어 있었음 | 10/22 운영에 반영 | 32 → 33 (3위 안 40) |

- **본문을 뺀 이유**: 스킬 본문(SKILL.md)은 스킬마다 구조가 비슷합니다. 본문을 넣으면 스킬끼리 벡터가 서로 가까워집니다. 그래서 짧은 검색어와의 점수가 모든 스킬에서 0.3~0.4대로 몰려 1위가 잘 갈리지 않았습니다.
- **태그 가산점을 없앤 이유**: 틀린 스킬도 태그로 가산점을 받았습니다. 1위를 놓친 15개 모두 1위 스킬이 태그 가산점을 받은 경우였습니다. 태그 2개 이상일 때만 주기, 흔한 태그 빼기, 드문 태그일수록 크게 주기도 해 봤지만 26~29로 가산점 없음(30)보다 못했습니다.
- **이름·ID가 +0.3인 이유**: 사용자가 스킬을 이름으로 콕 집어 부르면 1위로 나와야 합니다. 1.0으로 확정하지 않은 이유는 흔한 단어 이름(slack, handoff, 회고 등)이 지나가듯 걸리기 때문입니다. 점수가 1.0보다 낮으면 추천 기준에서 걸러질 여지가 남습니다.
  - ID(`write-post`)와 띄어쓰기 없는 영문 이름은 단어 단위로 맞춥니다. `post`만 써서는 `write-post`에 걸리지 않습니다.
  - 그 밖의 이름(`회고`, `Receiving Code Review`)은 검색어 안에 들어 있으면 맞은 것으로 봅니다. 조사가 붙어도 걸립니다.
  - 작업 설명(`--context`)은 임베딩에만 쓰고 이름 맞추기에는 쓰지 않습니다.

남은 문제:

- 흔한 단어 ID가 지나가듯 걸립니다. 스킬이 필요 없는 검색 25개 중 4개(handoff 1개, slack 3개)에서 1위가 됐습니다.
- 이름·ID 가산점 때문에 점수가 1을 넘을 수 있습니다(harness-snapshot 1.04). 상한은 아직 정하지 않았습니다.
- 41개는 한 사람(안재민)의 검색 기록입니다. 1~2개 차이는 우연일 수 있습니다. 본문 빼기(19 → 30)처럼 큰 차이만 믿을 만합니다.
- 운영에 넣으려면 516개 전체 임베딩을 다시 만들어야 합니다. 운영 DB 변경이라 승인을 받은 뒤 runbook대로 합니다.

## 요약 2. 스킬끼리 유사도 (중복 찾기)

여기서 쓰는 임베딩은 중복 찾기 전용입니다. 검색에 쓰는 운영 임베딩(요약 1, 이름·설명·태그만)과는 따로 만듭니다. 중복 찾기용 임베딩을 운영 어디에 저장할지는 아직 정하지 않았습니다.

처음에는 스킬 본문을 그대로 임베딩해서 점수를 매겼습니다. 그랬더니 하는 일이 다른 스킬이 높게 나오거나 같은 스킬이 낮게 나오는 경우가 많았습니다. 원인을 하나씩 빼거나 바꾸면서 점수가 어떻게 달라지는지 봤습니다.

| 바꾼 것 | 왜 | 바꾸기 전 → 후 | 절 |
| -- | -- | -- | -- |
| **여러 스킬에 똑같이 나오는 줄을 빼고 임베딩** (3개 이상 스킬에 같은 줄, 본문의 약 10%) | gstack 스킬들은 앞에 같은 안내문이 길게 있어서 하는 일이 달라도 점수가 높았습니다 | gstack-codex ~ gstack-plan-ceo-review: 0.96 → 0.64<br>진짜 같은 스킬 codex-slides ~ slides: 0.98 → 0.99 (그대로 높음)<br>0.85 이상 쌍: 143개 → 17개 | 1 |
| **점수 기준값 대신 순위로 후보 뽑기** (스킬마다 가장 비슷한 5개) | 설명 언어가 다르면 같은 스킬도 점수가 낮게 나왔습니다. codex-slides(한국어 설명) ~ slides(영어 설명)는 설명 점수 0.66 | 언어가 달라도 후보에 들어옵니다. codex-slides에서 slides는 설명 기준 4위, 본문 기준 1위 | 2 |
| **중복 찾기는 설명 대신 본문으로 비교** | 중복은 실제로 하는 일이 같은지가 중요합니다. 본문만 쓰면 설명 언어가 섞이는 문제도 없어집니다 | 후보 1,102쌍을 AI가 나눠 복사본 20쌍, 같은 일 49쌍을 찾았습니다 | 3 |
| **긴 본문을 잘라 쓰지 않고 조각으로 나눠 가장 높은 조각 점수 사용** | 임베딩 모델은 8,191토큰까지만 받아서 긴 스킬 22개는 앞부분만 들어갔습니다 | 점수 높은 600쌍 중 33쌍이 달라졌습니다. stibee-report ~ gpters-newsletter-v2: 0.612 → 0.832 | 4 |
| **긴 스킬 22개는 요약해서 임베딩** (최종 채택) | 조각 최고점은 겹치는 한 부분만 보고 점수를 높게 매겼습니다 | 같은 스킬 쌍이 다른 쌍보다 높게 나온 비율: 86% → 93%<br>복사본 평균 0.686 → 0.749, 다름 평균 0.585 → 0.588 (다른 쌍은 거의 그대로)<br>가장 비슷한 1위가 나아진 스킬 3개, 나빠진 것 0개 | 4 |

정한 것:

- **임베딩 한도를 넘는 긴 스킬 22개만 요약해서 임베딩합니다. 나머지 494개는 원문 그대로 씁니다.** 한도 안에 들어오는 스킬은 이미 본문 전체가 들어가므로 요약하면 정보만 줄어듭니다.
- 유사도 점수만으로 같은 스킬인지 정하지 않습니다. 점수로는 후보만 뽑고 같은지 다른지는 AI가 본문을 읽고 나눕니다. 점수가 가장 높은 13쌍을 글자로 비교해 보니 거의 그대로 복사한 것은 4쌍뿐이었습니다(5절).

비슷한 스킬은 43묶음, 스킬 101개를 찾았습니다(3절). 이 묶음은 3절 방식(공통 줄을 뺀 본문, 긴 스킬은 앞부분만)으로 찾은 것입니다. 긴 스킬 요약 방식으로는 아직 묶음을 다시 만들지 않았습니다. 아직 아무것도 지우거나 숨기지 않았습니다.

남은 문제:

- gstack 공통 안내문은 요약하지 않은 스킬에 그대로 남아 있어서 gstack끼리는 여전히 0.73~0.85입니다.
- 요약 비교에 쓴 같은 스킬 쌍이 6개뿐이라 차이가 크다고는 할 수 없습니다.

주의할 것:

- AI 판단은 Claude가 한 번씩, 본문 앞 900자만 보고 했습니다. 다른 AI나 사람이 다시 확인하지 않았습니다.
- 데이터는 10/21에 운영에서 복사해 온 것입니다.

## 0. 검색 점수 실험 (10/21 ~ 10/22)

### 시험용 검색 41개를 만든 방법

**1. 검색 기록 모으기**

- 안재민 컴퓨터의 Claude Code 세션 기록(`~/.claude/projects/*/*.jsonl`, 파일 3,189개)을 읽었습니다.
- 그 안에서 AI가 직접 실행한 `aitk search '...'` 명령을 모두 찾았습니다. 205번이 나왔고 똑같은 검색어를 빼니 172개였습니다. 기간은 2026-09-06 ~ 10-20입니다.
- 이번 실험 중에 돌린 검색을 빼고 **161개**를 남겼습니다.
- Codex 기록과 MCP로 한 검색은 들어 있지 않습니다. 다른 팀원 기록도 없습니다.

**2. 스킬이 필요했던 검색만 고르기**

- Claude와 Codex가 각각 검색 바로 앞의 사용자 메시지를 보고 "이 상황에 팀 스킬이 필요했나"를 판단했습니다.
- 둘 다 필요하다고 한 것 82개, 둘 다 필요 없다고 한 것 55개, 엇갈린 것 24개였습니다. **82개**만 다음 단계로 넘겼습니다.

**3. 정답 스킬 정하기**

- 검색어마다 옛 방식과 새 방식의 상위 5개를 합쳐 후보를 만들었습니다(평균 7.6개). 어느 방식에서 나온 후보인지 지우고 순서를 섞었습니다. 판단하는 AI가 한쪽 방식 편을 들지 못하게 하려는 것입니다.
- 후보마다 이름, 설명, 태그, 본문 앞 800자를 붙이고 검색 직전 사용자 메시지(600자까지)도 같이 줬습니다.
- Claude(서브에이전트 4개가 나눠서)와 Codex가 각각 후보마다 점수를 매겼습니다. 2는 "이 상황에 불러오면 바로 도움", 1은 "일부만 도움", 0은 "도움 안 됨"입니다. 단어가 겹치는지가 아니라 사용자가 실제로 필요했던 것을 보게 했습니다.
- **두 AI가 모두 2를 준 스킬이 있는 41개**를 정답으로 썼습니다. 정답 스킬은 하나일 수도 여러 개일 수도 있습니다. 예를 들어 글 다듬기 검색은 humanizer, de-ai-ify, stop-slop 셋 다 정답입니다.
- 두 AI 모두 2를 준 후보가 없는 25개는 "맞는 스킬 없음"으로 둡니다. 이 25개는 필요 없는 추천을 셀 때만 씁니다. 한쪽만 2를 준 16개는 뺐습니다.

**4. 채점**

- 검색 결과 1위가 정답 스킬 가운데 하나면 맞은 것으로 셉니다.
- 본문이 거의 같은 13쌍(본문 유사도 0.90 이상, 4절)은 같은 스킬로 보기로 했습니다. 정답이 그중 하나면 짝이 1위로 나와도 맞은 것으로 셉니다. 다만 41개 정답에 13쌍의 스킬이 하나도 없어서 이 규칙은 점수에 영향을 주지 않았습니다.

**이렇게 정한 이유**

- 처음에는 정답 스킬을 보고 질문을 직접 만들어 봤습니다. 질문에 정답 스킬의 태그 단어가 들어가기 쉬워서 새 방식에 유리했습니다.
- 다음에는 실제 기록에서 검색 뒤에 불러온 스킬(`aitk get`)을 정답으로 써 봤습니다. 불러온 스킬은 그때 옛 방식이 보여 준 결과 중에서 고른 것이라 옛 방식에 유리했습니다.
- 그래서 출처를 가린 후보를 AI 둘이 따로 판단하고 둘 다 동의한 것만 정답으로 남겼습니다.

**한계**

- 한 사람의 개발 작업 위주 기록입니다.
- 두 방식 모두 상위 5개에 못 올린 스킬은 정답이 될 수 없습니다.
- 두 AI가 동의한 것만 남겨서 애매한 검색이 빠졌습니다. 실제보다 쉬울 수 있습니다.
- 정답은 AI 판단이고 사람이 전부 확인하지는 않았습니다.
- 41개라 1~2개 차이는 우연일 수 있습니다.

## 1. 점수로 비교할 때 생긴 문제 (10/21)

처음에는 점수만으로 비슷한 스킬을 고를 수 있는지 봤습니다. 임베딩은 OpenAI text-embedding-3-large(3,072차원)를 썼습니다.

- **공통 안내문**: gstack 스킬들은 본문 앞에 같은 안내문이 길게 들어 있습니다. 그래서 하는 일이 달라도 본문 유사도가 0.96쯤 나옵니다.
- **본문 언어**: 본문 언어가 같으면 하는 일이 달라도 점수가 0.1~0.2쯤 높게 나옵니다. humanizer(영어 본문)와 이미지 생성 스킬이 0.60인데, 한국어 본문인 write-post와는 0.40입니다. 516개 중 341개가 영어 본문입니다.
- **설명 언어**: 같은 스킬도 설명 언어가 다르면 설명 점수가 낮습니다. codex-slides(한국어 설명)와 slides(영어 설명)는 설명 0.66, 본문 0.98입니다.
- 설명 점수가 높은 쌍이 본문 점수도 높은 경우는 생각보다 적습니다. 두 점수의 상관계수(1이면 늘 같이 오르내림)는 전체 13만여 쌍에서 약 0.48입니다. 어느 점수든 0.6 이상인 쌍만 보면 0.30으로 더 낮습니다.

해 본 것:

- 3개 이상 스킬에 똑같이 나오는 줄을 빼고 본문 임베딩을 다시 만들었습니다. 본문의 약 10%가 빠졌습니다.
  - gstack-codex ~ gstack-plan-ceo-review: 0.96 → 0.64로 내려갔습니다.
  - codex-slides ~ slides: 0.98 → 0.99로 높게 남았습니다.
- 유사도 0.85 이상 쌍은 설명 기준 22개, 본문 그대로 143개, 공통 줄 뺀 본문 17개였습니다.
- 설명 점수와 공통 줄 뺀 본문 점수의 평균이 0.68 이상인 것끼리 이으면 52묶음, 스킬 160개입니다.

## 4. 본문 전체 임베딩 (10/22)

3절에서 AI는 본문 앞 900자만 봤습니다. 10/22에는 공통 줄을 빼지 않은 본문 전체로 유사도를 다시 냈습니다.

긴 본문은 이렇게 처리했습니다.

- 임베딩 모델은 한 번에 8,191토큰(글자 조각 단위, 한국어는 대략 한 글자에 1~2토큰)까지만 받습니다. 516개 중 22개가 이보다 길었습니다.
- 긴 본문은 줄 단위로 쌓다가 8,191토큰을 넘기 직전에 끊어 조각으로 나눴습니다(최대 4조각). 문장 중간에서 잘리지 않게 하려는 것입니다. 한 줄이 혼자 8,191토큰을 넘을 때만 토큰 단위로 잘랐습니다.
- 두 스킬의 조각을 모두 짝지어 비교하고 가장 높은 점수를 썼습니다. 조각 점수의 평균은 쓰지 않았습니다. 평균을 내면 긴 스킬의 일부가 다른 스킬과 똑같아도 점수가 묻힙니다.
- 비교용으로 첫 조각끼리만 비교한 점수도 남겼습니다. 점수가 높은 600쌍 중 두 점수가 다른 쌍은 33쌍이었습니다. 예를 들어 stibee-report ~ gpters-newsletter-v2는 첫 조각 0.612, 가장 높은 조각 0.832입니다.

| 본문 전체 유사도 | 쌍 수 |
| -- | -- |
| 0.95 이상 | 6 |
| 0.90 이상 | 13 |
| 0.85 이상 | 23 |
| 0.80 이상 | 58 |

0.90 이상 13쌍은 검색 실험을 채점할 때 같은 스킬로 쳤습니다. 검색 실험은 실제 검색 기록 41개에 정답 스킬을 정해 두고 검색 결과 1위가 정답인지 본 것입니다. 정답이 13쌍 중 하나라면 짝이 되는 스킬이 1위로 나와도 맞은 것으로 셌습니다. 실제로는 41개 정답에 13쌍의 스킬이 없어서 점수가 달라지지 않았습니다. 이 13쌍은 채점용으로만 정했고 정리 대상으로 정한 것은 아닙니다.

### 긴 스킬은 요약해서 임베딩 (10/23)

**결정: 8,191토큰을 넘는 스킬(22개)만 요약해서 임베딩합니다. 나머지 494개는 원문 그대로 임베딩합니다.** 제한 안에 들어오는 스킬은 본문 전체가 이미 한 번에 들어가므로 요약하면 정보만 줄어듭니다.

해 본 방법:

- 긴 스킬 22개를 Claude(sonnet)로 줄였습니다. 원문 언어는 그대로 둡니다. 하는 일·쓰는 때·입력·결과·단계·규칙은 남기고 반복과 긴 예시부터 줄이게 했습니다.
- 처음에는 "6,000토큰 이내"로 요청했는데 6개가 여전히 제한을 넘었습니다. 대부분 한국어 스킬이었습니다. 이 6개는 "9,000자 이내"로 다시 요약했습니다. feedback-coach는 "7,000자 이내"로 한 번 더 줄였습니다. 그 뒤로는 22개 모두 8,191토큰 안에 들어왔습니다(가장 짧은 것은 약 2,500토큰).
- 요약을 임베딩해서 나머지 스킬(원문)과 비교했습니다.

3절에서 AI가 나눠 둔 쌍 가운데 긴 스킬이 들어간 98쌍(복사본 3, 같은 일 3, 겹침 59, 다름 33)으로 비교했습니다.

| | 조각 최고점 | 요약 |
| -- | -- | -- |
| 복사본 평균 점수 | 0.686 | 0.749 |
| 같은 일 평균 점수 | 0.660 | 0.703 |
| 겹침 평균 점수 | 0.669 | 0.681 |
| 다름 평균 점수 | 0.585 | 0.588 |
| 복사본·같은 일 쌍이 다름 쌍보다 높게 나온 비율 | 86% | 93% |
| 복사본·같은 일 쌍이 겹침·다름 쌍보다 높게 나온 비율 | 65% | 76% |

- 같은 쌍의 점수는 오르고 다름 쌍의 점수는 거의 그대로여서 둘이 더 잘 갈립니다. semgrep-security-scan ~ static-analysis(복사본)는 0.606 → 0.774, security-static-analysis ~ static-analysis(같은 일)는 0.626 → 0.710입니다.
- 일부만 겹치는 쌍은 점수가 내려갑니다. stibee-report ~ gpters-newsletter-v2는 0.832 → 0.75입니다. 조각 최고점은 겹치는 한 부분만 보고 높게 매겼습니다. 요약은 하는 일 전체를 봅니다. 비슷한 스킬을 찾는 목적에는 요약 쪽이 맞습니다. 한쪽이 다른 쪽을 통째로 포함하는 쌍은 5절의 글자 비교로 따로 찾습니다.
- 스킬마다 가장 비슷한 5개는 22개 중 14개가 4개 이상 그대로였습니다. 1위가 확실히 나아진 것은 3개입니다. static-analysis(gstack-qa → semgrep-security-scan), ai-talk-post(gpters-daily-content-v2 → ai-talk-manager), shadcn-ui(next-best-practices → tailwind-v4-shadcn)입니다. 나빠진 것은 없었습니다.

한계와 운영할 때 챙길 것:

- 복사본·같은 일 쌍이 6개뿐이라 차이가 크다고는 할 수 없습니다. 쌍이 늘면 다시 확인합니다.
- 요약은 돌릴 때마다 조금씩 달라집니다. 만든 요약을 저장해 두고 스킬 본문이 바뀔 때만 다시 만듭니다.
- AI가 요약 길이를 잘 지키지 못합니다. 요약 뒤 토큰 수를 세서 넘으면 다시 줄이는 단계가 필요합니다.
- gstack 공통 안내문 문제는 그대로입니다. 요약하지 않은 쪽 스킬에는 안내문이 남아 있어서 gstack끼리는 여전히 0.73~0.85입니다.

## 6. 남길 쪽을 정하는 기준 (제안)

1. 실제로 많이 쓰이는 쪽 (운영 사용 기록)
2. 관리되고 있는 쪽 (최근 수정, 판, 올린 사람이 활동 중인지)

지우지 않고 검색에서만 빼면 잘못 골라도 되돌릴 수 있습니다. 같은 일, 다른 출처 묶음은 고르지 않고 설명을 서로 다르게 고치는 방법도 있습니다.
