# 생산성 복리 엔진 — 로드맵

> 기간: 2/24(월) ~ 3/6(금) · 담당: 1명 · 대상: GPTers 내부 (→ 퍼블릭 확장 판단)

---

## 핵심 요약

AI 스킬 자동 추천 시스템이 작동하고 있으나, 추천 적중률이 20%(목표 30%)로 미달입니다.
2주간 (1) 추천 적중률을 전면 개선하고, (2) 스킬의 실제 효용을 세 가지 접근으로 검증합니다.
3/6에 Go/No-go 판단을 통해 퍼블릭 확장 여부를 결정합니다.

**핵심 질문:** 추천이 정확해져도, 스킬 자체가 생산성을 높이는가?

---

## 용어 정의

| 용어 | 정의 | 예시 |
|------|------|------|
| **추천 적중률** | AI가 추천한 스킬 중 사용자가 실제로 조회한 비율 | "환불 처리해줘" → AI가 환불 자동화 스킬 추천 → 사용자가 조회함 = **적중**. 10번 추천 중 2번 조회하면 적중률 20%. |
| **검색 무결과율** | 실제 검색이 필요한 경우 중 카탈로그에 관련 스킬이 없어 결과가 0건인 비율 | "Remotion으로 영상 만들어줘" → 검색했으나 관련 스킬이 카탈로그에 없음 = **무결과**. "계속해" 같은 후속 메시지는 검색 대상에서 제외. |

---

## 현재 상황 요약

**"AI가 알아서 필요한 스킬을 찾아준다"** — 이 핵심 기능은 작동하고 있습니다.

AI 코딩 도구로 작업하면, AI가 대화 맥락을 분석하여 관련 스킬을 자동 추천합니다. 지난 7일간 77건의 자동 추천이 발생했습니다.

**문제는 추천의 적중률입니다.**

추천은 발생하지만, 10번 중 8번은 관련 없는 스킬을 보여줍니다. "슬랙 자동화 만들어줘"라고 했는데, 전혀 관련 없는 스킬이 나오는 식입니다.

| 지표 | 시작 (2/20) | 현재 | 의미 |
|------|-----------|------|------|
| 추천 적중률 | 5% | **20%** | 10번 추천 시 2번 적중 |
| 검색 무결과율 | 90% → *측정 보정* | **14%** | 관련 스킬이 카탈로그에 없는 비율 |

초기 90%는 측정 방식의 문제였습니다. "계속해", "ㅇㅇ" 같은 후속 메시지까지 전부 검색을 시도하여 당연히 결과가 없는 경우도 "실패"로 카운트되었습니다. 후속 메시지 필터링과 관련도 점수 필터링을 적용한 뒤, **실제로 검색이 필요한 경우만 측정**하면 14%입니다. 이 14%가 "관련 스킬이 카탈로그에 없는 실제 실패"를 의미합니다.

추천 적중률은 1주 만에 5% → 20%로 개선되었으나, 목표(30%)에는 아직 미달입니다.

그런데 더 근본적인 질문이 있습니다: **추천이 정확해져도, 스킬 자체가 실제로 생산성을 높이는가?**

---

## 분석: 왜 80%가 빗나가고, 써도 효용이 없는가

### 추천이 빗나가는 세 가지 원인

**1. AI가 사용자 의도를 제대로 전달하지 못합니다 (가장 큰 원인)**

"슬랙에서 특정 멘션을 자동 수집하는 봇 만들어줘"라고 하면, AI가 **"slack message search"**라는 키워드로 축약하여 검색합니다. 원래 의도의 상당 부분이 손실됩니다.

**2. 찾는 스킬이 아예 없습니다 (~14%)**

SMS 알림, Remotion 비디오 같은 스킬은 아직 제작되지 않았습니다. 없는 것을 아무리 잘 찾아도 결과가 나올 수 없습니다.

**3. 검색이 느립니다 (2.6초)**

검색 1회에 2.6초가 소요됩니다. 현재 타임아웃이 없어 검색이 느리다고 추천이 건너뛰어지지는 않지만, 사용자 응답 지연의 원인이 됩니다.

### 스킬을 찾아도 효용이 없는 문제

초기 사용자 피드백에서 두 가지 중요한 신호가 나왔습니다.

**1. "외부 스킬을 가져다 써도 생산성 향상을 크게 못 느낀다"**

현재 카탈로그에는 73개의 스킬이 있습니다. 실제 사용 데이터를 보면 뚜렷한 패턴이 있습니다.

**잘 쓰이는 스킬 — "내부 업무 자동화"**

| 스킬 | 30일 조회 | 하는 일 |
|------|----------|---------|
| 상품/쿠폰 관리 | 30회 | 쿠폰 발급, 상품 생성 자동화 |
| 에어테이블 연동 | 14회 | 데이터 연동 셋업 |
| 내부 API 가이드 | 13회 | 사내 API 사용법 안내 |
| DB 접근 가이드 | 12회 | 운영 DB 조회 방법 |
| 문자/이메일 발송 | 5회 | 수신자 목록으로 일괄 발송 |
| 환불 자동 처리 | 4회 | 에어테이블 → 환불 → SMS 안내 |

공통점은 **특정 업무를 '끝까지' 자동화**한다는 것입니다. 수동으로 30분 걸리는 일을 스킬 하나로 해결합니다.

**안 쓰이는 스킬 — "개발 방법론"과 "일하는 방식 변화"**

| 스킬 | 30일 조회 | 하는 일 |
|------|----------|---------|
| 병렬 에이전트 디스패치 | 0회 | 여러 작업을 동시에 처리 |
| 서브에이전트 개발 | 0회 | 에이전트 기반 개발 워크플로우 |
| 계획 실행 | 0회 | 구현 계획을 단계별로 실행 |
| TDD | 0회 | 테스트 먼저 작성 후 구현 |
| 체계적 디버깅 | 0회 | 4단계 근본 원인 분석 |
| 브레인스토밍 | 0회 | 아이디어를 설계로 발전 |

**"일하는 방식을 바꾸는" 스킬은 이미 10개 이상 만들어져 있습니다.** 문제는 사용되지 않는다는 것입니다. 방법론 스킬은 당장의 필요가 아닌 습관의 변화를 요구하기 때문입니다.

**2. 대화 로그 분석에 대한 거부감**

스킬 추천을 위한 대화 맥락 수집에 대해 거부감 피드백이 있었습니다. 이 이슈는 퍼블릭 배포 시 별도 설계 과제로 남겨둡니다.

### 결론: 두 축으로 정리

위 데이터를 종합하면, 이번 검증에서 답해야 할 질문은 두 축으로 나뉩니다.

**축 1. 스킬 유형 — "무엇이 퍼블릭에서 통하는가"**

스킬은 외부 이식 가능 여부에 따라 두 유형으로 나뉩니다.

| 유형 | 예시 | 효용 | 현재 상태 | 퍼블릭 가치 |
|------|------|------|----------|------------|
| 내부 전용 | 쿠폰 발급, 환불 처리, 문자 발송 | 30분 → 1분 | ✅ 잘 쓰임 | ❌ 이식 불가 |
| 범용 | TDD, 계획→실행, 코드 리뷰, 디버깅 | 개발 품질 향상 | ❌ 조회 0회 | ✅ 어디든 적용 |

카탈로그 73개 중 **38개(52%)가 이미 범용 스킬**입니다. 그런데 조회 TOP 6개는 전부 내부 전용입니다. 퍼블릭에서 통하려면 "범용 스킬이 왜 안 쓰이는가"를 풀어야 합니다.

**축 2. 플랫폼 가치 — "왜 플랫폼이어야 하는가"**

스킬 유형과 별개로, 이 플랫폼이 존재해야 할 이유가 있는지를 검증해야 합니다. 스킬은 파일 하나로 만들 수 있고, 위키나 공유 폴더로도 배포할 수 있습니다. 플랫폼만이 제공하는 가치는 **"몰랐거나 잊고 있던 스킬을 AI가 필요한 순간에 찾아주는 것"** — 즉 발견의 가치입니다. 이것은 내부 전용 스킬에도, 범용 스킬에도 똑같이 적용됩니다.

| | 발견의 가치가 작동하면 | 작동하지 않으면 |
|---|---|---|
| **내부 전용** | 환불 처리를 시작하면 AI가 자동으로 환불 자동화 스킬 추천 | 스킬이 있는 줄 모르고 수동으로 30분 작업 |
| **범용** | 기능 개발을 시작하면 AI가 TDD 스킬 추천 | 위키에 올려도 아무도 안 봄 (현재 상태) |

발견의 가치가 작동하지 않으면, 플랫폼 대신 위키 문서로 충분합니다. 이것이 Go/No-go 필수 조건 #3("발견의 가치" 사례 1건+)을 두는 이유입니다.

## 해결 전략

두 가지 문제("추천이 빗나간다", "써도 효용을 못 느낀다")를 각각 어떻게 해결할 것인지 정리했습니다.

### 전략 1: 추천 적중률 전체 개선

AI가 스킬을 추천하는 과정은 6단계를 거칩니다. 어느 한 단계에서 이탈하면 추천은 실패합니다.

```
① 작업 감지 → ② 추천 필요 여부 판단 → ③ 검색어 생성 → ④ 스킬 매칭 → ⑤ 관련도 필터 → ⑥ 추천/적용
```

| 단계 | 문제 | 개선 방향 |
|------|------|----------|
| ① 작업 감지 | 없음 (정상 작동) | — |
| ② 추천 필요 여부 판단 | 보수적 판단으로 스킵 발생 | 판단 기준 명확화 |
| ③ 검색어 생성 | **사용자 의도 손실** (가장 큰 원인) | 키워드뿐 아니라 작업 맥락까지 함께 전달 |
| ④ 스킬 매칭 | 스킬 설명이 부실하여 매칭 실패 (29%) | 스킬 설명 보강 |
| ⑤ 관련도 필터 | 필터 기준값 적절성 미검증 | 실패 데이터 분석으로 최적값 도출 |
| ⑥ 추천/적용 | 추천 후 실제 사용율 20% | "왜 이 스킬인지" 맥락 제시 |

**가장 큰 개선 포인트 — ③ 검색어 생성**

현재: "슬랙 멘션 자동 수집 봇 만들어줘" → AI가 **"slack search"** 2단어로 축약해서 검색
개선: 키워드 + "슬랙 멘션 자동 수집 봇 구현, 에어테이블 연동 완료"라는 작업 맥락을 함께 전달

맥락을 함께 보내면 사용자가 실제로 원하는 것에 가까운 스킬을 찾을 수 있습니다.

**두 번째 개선 — ④ 스킬 설명 보강**

스킬의 설명과 태그가 부실하면 아무리 잘 검색해도 매칭이 안 됩니다. 현재 73개 중 설명이 충분한 것은 62%이고, 29%는 보통, 10%는 태그가 아예 없습니다. 기존 스킬의 설명을 보강하고, 신규 스킬 등록 시에도 품질을 자동으로 체크합니다.

**나머지 단계 — 데이터 기반 최적화**

추천 실패 로그를 분석하여 ② 판단이 너무 보수적인 경우, ⑤ 필터 기준값이 부적절한 경우, ⑥ 추천은 됐는데 클릭하지 않는 경우를 각각 데이터로 파악하고 개선합니다.

### 전략 2: 효용성 — 세 가지 접근을 각각 검증

내부 업무 자동화만 검증하면 퍼블릭에서 의미 없는 실험이 됩니다. 세 가지 접근 모두를 이번 기간에 테스트합니다.

| 접근 | 검증할 것 | 퍼블릭 가치 |
|------|----------|------------|
| A: 내부 자동화 | 추천 적중률이 올라가면 기존 스킬 사용이 늘어나는가 | 플랫폼 작동 증명 |
| B: 외부 스킬 수집 | 카탈로그가 풍부해지면 추천 적중과 무결과율이 개선되는가 | 퍼블릭 카탈로그 기반 |
| C: 발견의 가치 | 추천 덕분에 몰랐던 스킬을 쓴 사례가 나오는가 | 플랫폼 존재 이유 |

**접근 A: 내부 업무 자동화 — 기존 스킬의 매칭 개선 (증명된 가치, 내부 전용)**

조회 TOP 스킬(쿠폰, 환불, 문자)은 이미 효용이 입증되어 있습니다. 문제는 추천이 빗나가는 것이므로, 전략 1(검색어 생성 개선 + 스킬 설명 보강)을 적용하여 매칭 정확도를 높입니다. 별도의 신규 스킬 제작은 하지 않습니다.

단, 이 스킬들은 GPTers 내부 API/DB에 의존하므로 **퍼블릭에서는 직접 이식이 불가능**합니다. 내부에서의 역할은 "플랫폼이 작동한다는 증명"입니다.

**접근 B: 외부 고품질 스킬 수집 — 카탈로그 밀도 확보 + 무결과율 감소**

"발견의 가치"가 작동하려면 카탈로그에 **찾을 만한 스킬이 충분히 있어야** 합니다. 현재 범용 스킬 38개는 내부에서 제작한 것이라 범위가 한정적입니다. 무결과 검색(14%)의 상당 부분도 카탈로그에 해당 스킬이 없기 때문이며, 직접 제작하는 대신 외부의 검증된 스킬을 수집하여 효율적으로 채웁니다.

| 수집 출처 | 예시 | 기대 효과 |
|----------|------|----------|
| GitHub 오픈소스 | 커뮤니티 스킬 레포, awesome-claude-code 등 | 개발 워크플로우 스킬 확충 |
| Cursor Rules | 프레임워크별 베스트 프랙티스 (Next.js, Supabase 등) | 기술 스택별 가이드 확보 |
| 공식 문서 기반 | Vercel, Supabase, Stripe 등의 API 패턴을 스킬화 | 통합/연동 작업 시 즉시 활용 |

검증된 것만 선별하고, 재배포 가능한 라이선스(MIT/Apache)만 대상으로 합니다. 목표는 **10~15개** 고품질 스킬 추가입니다.

단, 기존 38개 범용 스킬도 조회 0회인 상태이므로, 외부 스킬 수집은 추천 적중률 개선(전략 1)과 병행하되, 수집한 스킬의 설명/태그 품질을 높여서 추가합니다.

**접근 C: "혼자 만들면 되는데 왜 공유하는가?" — 플랫폼 존재 이유 검증**

스킬은 혼자서도 만들 수 있습니다. 이 플랫폼에 올려서 공유해야 할 이유가 있는지 검증해야 합니다.

로컬(개인 PC)에만 스킬을 두면 **"내가 아는 것만 쓸 수 있다"**는 한계가 있습니다. 직접 만들었거나, 누군가 알려준 스킬만 사용할 수 있습니다. 3개월 전에 만든 스킬도 잊으면 다시 수동으로 작업하게 됩니다.

플랫폼의 유일한 가치는 **"몰랐거나 잊고 있던 스킬을 AI가 필요한 순간에 찾아주는 것"**입니다.

- 로컬: "환불 자동화 스킬이 있다는 걸 모르면 수동으로 30분 작업"
- 플랫폼: "환불 처리를 시작하면 AI가 자동으로 환불 자동화 스킬을 추천"

**스킬을 만드는 것이 아니라 발견하는 것**이 공유의 효용입니다. 단, 이것이 작동하려면 **추천이 정확해야** 합니다 (전략 1). 추천이 80% 빗나가면 공유의 효용도 없습니다. 전략 1이 전략 2의 전제 조건입니다.

검증 항목:
- "이런 스킬이 있는 줄 몰랐는데 추천받아서 썼다"는 사례가 나오는가?
- 이 사례가 나오지 않으면, 플랫폼이 아니라 위키 문서로 충분합니다.

## 실행 계획

**투입 리소스:** 1명이 2주간 전담합니다. 따라서 항목별 우선순위를 구분하여, 핵심(P0)부터 처리하고 나머지는 여력에 따라 진행합니다.

### 1주차 (2/24~2/28): 추천 개선 + 카탈로그 확충

**P0 (반드시 완료):**
- 검색어에 작업 맥락을 함께 전달하도록 개선 (전략 1 — 가장 큰 병목 해소)
- 기존 스킬 설명 보강 — 설명 부실 21개 + 태그 없는 7개 (전략 1)
- 외부 고품질 스킬 수집 — 10~15개 목표 (전략 2-B) — 카탈로그 밀도 확보 + 무결과율 감소

**P1 (가능한 완료):**
- 추천 실패 데이터 분석 — 어디서 이탈하는지 파악
- 신규 스킬 등록 시 품질 자동 체크 추가 (전략 1)
- 검색 속도 개선 (전략 1, 현재 2.6초)

**P2 (여력에 따라):**
- 사용 기록 수집 시작 (전략 2-C)

### 2주차 (3/3~3/6): 측정 + 판단

- 검색 속도 최적화 마무리 (목표: 1.5초 이내)
- 단계별 전환율 측정 (작업 감지 → 판단 → 검색 → 필터 → 추천)
- 직접 사용하며 기록 — "이 플랫폼이 없었으면 사용하지 않았을 스킬이 있는가?"
- **3/6: Go/No-go 판단 — "퍼블릭에서 무엇을 내세울 것인가" 결론 도출**

## 성공 기준과 Go/No-go 판단 (3/6)

1인 체제에서 2주간 수집하는 데이터는 통계적 유의성을 갖기 어렵습니다. 아래 기준은 **"가설이 방향적으로 맞는가"를 판단하는 데 사용**하며, 확정적 결론이 아닌 방향성 확인입니다.

| # | 조건 | 기준 | 현재 | 구분 |
|---|------|------|------|------|
| 1 | 추천 적중률 | 30% 이상 | 20% | **필수** |
| 2 | 검색 무결과율 | 10% 이하 | 14% | 필수 |
| 3 | "발견의 가치" 사례 | 추천으로 몰랐던/잊고 있던 스킬을 실제 사용한 사례 1건+ | 0건 | **필수** |
| 4 | 검색 속도 | 1.5초 이내 | 2.6초 | 가산 |
| 5 | 외부 스킬 추천 적중 | 수집한 외부 스킬이 추천을 통해 실제 조회된 건수 1건+ | 0건 | 가산 |
| 6 | "시간 절약" 사례 | 스킬 덕분에 수동 대비 시간 절약을 기록한 건수 1건+ | 0건 | 가산 |

**각 수치의 근거와 한계:**

- **#1 적중률 30%** — 현재 20%에서 50% 상대 개선이며, 가장 큰 병목(검색어 의도 손실)을 개선하면 도달 가능한 수준으로 설정했습니다. 다만 "30%면 사용자가 유용하다고 느끼는가"에 대한 근거는 없습니다. 정확한 임계값은 이번 기간의 사용 기록에서 도출합니다.
- **#2 무결과율 10%** — 현재 14%이며, 반복되는 스킬 부재 패턴이 관찰되었습니다. 그러나 부재를 채워도 새로운 검색이 새로운 부재를 만들기 때문에 선형으로 감소하지 않습니다. "현재보다 개선된 방향"을 나타내는 목표이며, 정밀 계산에 기반한 수치는 아닙니다.
- **#3, #5 사례 1건+** — 존재 증명(existence proof)입니다. 0건이면 전제가 틀린 것이고, 1건이라도 있으면 개념은 작동합니다.
- **#4 속도 1.5초** — 현재 타임아웃이 없어 느리다고 추천이 스킵되지는 않지만, 검색 대기 시간이 사용자 응답 지연에 직접 기여합니다. 체감 차이가 얼마나 되는지는 미검증.
- **#6 시간 절약 1건+** — 1인 체제에서 통계적 의미를 갖는 건수를 정하기 어려우므로, 존재 증명으로 설정합니다. 측정은 자기 보고(self-report)이며 확증 편향이 작용할 수 있습니다.

**Go 조건:** 필수 3개(#1, #2, #3) 모두 충족 + 가산 3개 중 1개 이상 충족

**No-go 시 시나리오:**

| 상황 | 대응 |
|------|------|
| 필수 #1·#2 미달 (추천 품질 부족) | 추천 적중률 추가 개선 기간 2주 연장, 연장 후에도 미달 시 추천 기능 보류 |
| 필수 #3 미달 (발견의 가치 없음) | 플랫폼 → 위키 + 수동 검색으로 전환, 자동 추천 폐기 |
| 필수는 충족했으나 가산 전부 미달 | 스코프를 내부 도구로 축소, 퍼블릭 확장은 보류 |

## 솔직한 한계

이번 기간으로는 다음을 알 수 없습니다.

| 질문 | 이유 |
|------|------|
| 스킬을 배포한 뒤 실제로 활용했는가 | 검색→조회→배포 퍼널은 세션 추적으로 측정 가능하나, 배포 후 로컬 실행 여부는 추적 불가 |
| 외부 팀이 범용 스킬을 쓸 것인가 | 내부 검증 우선이며, 외부 반응은 다를 수 있음 |
| "발견의 가치"가 위키나 공유 폴더보다 나은가 | 대안 비교를 위해서는 더 긴 기간과 더 많은 사용자가 필요 |
| 프라이버시 설계 (수집 범위, 동의, opt-out) | 퍼블릭 배포 시 별도 설계가 필요 |

이 질문들은 **직접 사용 기록 + 각 접근별 결과 비교**로 일부 답을 얻고, Go/No-go에서 판단합니다.
